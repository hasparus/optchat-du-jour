# optchat-du-jour build spec

Oct 5, 2026 · Piotr Monwid-Olechnowicz (hasparus)

## Purpose and sources

We build optchat-du-jour, our own OptChat: Victor Taelin's endless chat whose history is its memory, kept as a binary summary tree. It runs on the Mac Mini and serves the MacBook and the phone over Tailscale. [docs/optchat.md](docs/optchat.md), Taelin's spec kept verbatim, is the source of truth; shitty-optchat is the reference implementation we mirror module for module where it agrees with it, without copying its code. This spec refers to docs/optchat.md by section and lists only what we add or do differently, and why.

What we add on top of the reference:

- A web UI (React + shadcn) with chat, memory browser and stats, next to a terminal client.
- Several devices: the Mac Mini owns memory; turns can run on the MacBook.
- Engines matched to the plans we already pay for: Claude Max for main turns, ChatGPT Pro for the compactor, an API key as overflow.

## Relationship to the reference implementation

docs/optchat.md is the source of truth, above the reference. Where they agree, the core matches shitty-optchat 1-1: same modules, same constants, same on-disk format, same turn mechanics. The reference follows the earlier gist; where docs/optchat.md changed something, we follow it (E22: the view's merge order, its sawtooth and `chat/view.json`, which the reference ignores) or say why not (E23–E26). We write every line ourselves from its SPEC, not from its source. Its data dir and ours must be interchangeable, so its `optchat view` can read our memory and vice versa (each folds its own view).

Rules:

- Everything the reference measured (ref §14) is taken as given until our own runs disagree. Re-run its probes after any Claude Code upgrade.
- Its deviations from the earlier gist (D1–D10, ref §11) apply unless this spec overrides them. Ours are numbered E1, E2, … and listed under Deviations.
- The pure kernel is written in Bend 2 and compiled to JavaScript (E14): `id+n` addressing, the merge order (`fit`), the view's sawtooth, the rebuild from the log and the pump's rule 3. The laws under "Bend laws" are proved; what they leave open (which pair `fit` merges, and the rebuild's relation to the log) is tested against a model and the reference. It never sees text, only sizes as integers.
- Effect is the runtime for everything with I/O, time or concurrency (E13), and owns all text: rendering, cutting, logging.
- Tests follow ref §10: few, each a real failure scenario, with a fake `claude` and a fake compactor. No model calls in `bun test`: a preload (`test/preload.ts`) makes `claude` a stub that refuses to run unless a test names a fake, and points the secrets store at an empty file, so a test that forgets a fake fails instead of reaching a real model or key. The web UI's end-to-end server runs the fake `claude` with an empty secrets store too.

**Bend laws (`LAWS.bend`).** The compiler demands a proof of each on every edit:

1. The view tiles messages 0 to T with no gap and no overlap, after `fit`, `append` and the rebuild.
2. Every part `(l, i)` starts at `i · 2^l` and covers `2^l` messages; `coords` answers `(l, i)` for `id+n` exactly when `n = 2^l`, `id = i · 2^l` and `id + n ≤ T` (`coords_names`, `coords_complete`).
3. `fit` and the sawtooth merge only an adjacent sibling pair whose parent is built, and never split a part (`fit_merges`, `saw_merges`, `append_merges`); a view within its budget `fit` leaves unchanged (`fit_within`), and a view within `VIEW_HIGH` that owes no batch the sawtooth leaves unchanged (`saw_within`). Between batches the view only grows at its end: when the view after appending is within `VIEW_HIGH` and no batch is owed, `append` is the old view with the new line after its last (`append_grows`), so every turn's view is a prefix of the next one's (the cache property).
4. After `fit`, the view's size is at most its budget, or no pair can be merged (`fit_fits`). A batch ends at most `VIEW_LOW` or with no mergeable pair left, and owes the rest exactly when it ends over `VIEW_LOW` (`saw_batch`).
5. Rule 3 never offers a node whose children are unbuilt, nor one beyond the first unbuilt view line (`offers_allowed`); and it offers every node of the chat it allows, so the pump never stalls while there is work (`offers_complete`).

Not proved, and said so: which pair `fit` merges. That it is the most due one, ties to the leftmost (docs/optchat.md §3.2), is checked by `test/kernel.test.ts` against a literal model on seeded random runs and against Taelin's rollback push (every step t = 0..20,000 with push's list length as the budget, as docs/optchat.md §3.2 reports; the first-message rule matches at only 481), not by a law: a proof needs the cross-multiplied due comparison to be transitive, i.e. Nat lemmas on multiplication (monotonicity, cancellation by a positive power of two) that the proofs don't have yet. Laws 2 and 5 are exact, given the input test's one `levels` flag per node, which is what makes `offers_complete`'s `Within` premise safe: `coords_names` and `offers_allowed` are soundness (alone, they would hold for a `coords` that answered "No line" to every address and an `offers` that offered nothing), and `coords_complete` and `offers_complete` the converse. `fit_merges` is soundness only (see above), and no law says the rebuild equals appending every message (see the open questions). A false variant of each sawtooth law (`append_grows` while a batch is owed, `saw_batch` ending within `VIEW_HIGH` or never owing, `saw_within` while owing, either merge law with a line added or dropped) fails the check, and so do kernels that merge at every message, never owe a batch, ignore the debt, or drop the new line. The laws take their inputs at their word; `test/kernel.test.ts` checks on seeded random trees that what `src/kernel.ts` hands the kernel is the tree's: each line's built flag and size, its `ups` (non-empty exactly when its parent is built, and the parent a merge makes is that parent's own line), a view that tiles `[0, T)`, the marks and the debt it was given, and one `levels` flag per node of the chat.

The parity test runs the compiled kernel against the reference, which also guards against bugs in Bend's young compiler. If the M0 spike shows the JS output can't be called cleanly from TypeScript, the kernel is written in TypeScript and the laws become property tests.

**Parity test.** A script replays a fixture log through both implementations with the same deterministic fake compactor. It replays twice: caught up (the compactor finishes everything after each message), and lagging (`test/parity/fixture.ts`: 1,400 messages logged in batches ahead of the compactor, its calls released one at a time between batches, about one in five failing and retried after a short `retry`). The log must match byte for byte. The views part by design (E22): the reference merges by the first message at every message and node, we by the last message in batches, and the view's lines are each summary's context, so from the first merge in either view the summaries and rule 3's order part too. So the compactor calls, in order, and the tree records, in order, must match up to that point (each driver reports how many calls had started and nodes been built before its view first held a merged line; the shorter prefix is compared, about 375–475 calls and 1,650–1,710 nodes); every `optchat view`, ours or theirs, of either data dir, must be a well-formed view tiling the whole log; ours prints its saved view, and on the reference's dir (no `view.json`) rebuilds one and says so. It runs in CI against a pinned reference commit. Only options the reference's `openChat` already takes are used (`summarize`, `jobs`, `retryMs`); its checkout is never changed. The lagging replay is the one that sees rule 3's order: a pump that started its offers in another order passes the caught-up replay and fails this one.

## System shape

One server process on the Mac Mini owns memory; everything else is a client or a runner. Memory has a single writer, as docs/optchat.md §1 and the reference require.

- **Mac Mini, `optchat-server`** (launchd): log, tree, view, compactor pump, turn loop, priming, HTTP + WebSocket API, zoom/date MCP endpoint, and the built web UI as static files.
- **Every other machine, `optchat-device`** (launchd): spawns `claude -p` there when the server asks, streams its events back. The Mini needs none: the server spawns its own device's `claude` directly.
- **Clients:** the web UI (phone, MacBook, Mini) and the terminal REPL. Both speak the same WebSocket API.
- **Model engines:** Claude through the `claude` binary on a device; OpenAI through the Responses API with the ChatGPT plan token; an API key as overflow.

## Storage, tree, view and compactor ordering

Implement docs/optchat.md §1–§4 as ref §3 does, including its "as built" decisions, except where it lags docs/optchat.md (E22) or we keep the earlier gist (E23–E26).

- **Records:** `main` is `{i, kind, text, size, date}` with `kind` one of `user|talk|tool|echo|note` (E23); `tree` is `{l, i, text, size}`. A level-`l` node covers 2^l messages from `i * 2^l`.
- **Writes:** one write plus `fsync` per line, files split by local day, ids global. On load, skip and report damaged lines and add a missing final newline. Only the lock holder repairs.
- **Lock:** a unix socket per stream for the process lifetime; a refused connection means stale and taken over. Keep paths under ~107 characters.
- **Free nodes:** level 0 is `kind + ": " + text` if it fits in `NODE`; higher levels are `childA + "\n" + childB` if that fits. Written to `tree` like any node; no model call.
- **Pump:** rule 3 (E25): a node starts when it is unbuilt, its sources exist (its message; or both children built) and every view line before its end is built (for a message, every line before it). At most `JOBS` jobs, fixed 10 s retry, only the first failure of a node reported. The job's context is snapshotted when it starts.
- **View:** which pairs merge: the most due built pair, `due = (T − last) / 2^l` measured from the pair's last message, ties to the oldest (docs/optchat.md §3.2; the kernel compares `(1 + T − e₁)·2^l₂` against `(1 + T − e₂)·2^l₁`, `e` the pair's end). When: a message appends its line and nothing else changes; once the view passes `VIEW_HIGH`, one batch merges down to `VIEW_LOW`. A batch that parents not yet built stop over `VIEW_LOW` is owed (`folding`) and goes on at each later message until it reaches `VIEW_LOW`; a node being built never changes the view's lines. Never split. Size counts node text bytes, an unbuilt line its placeholder's. `fit(T, budget)` and the sawtooth take their marks as parameters, so a second view can run its own.
- **`view.json`:** `{"folding":bool,"view":[[l,i],…]}` in `chat/` beside `main/` and `tree/` (docs/optchat.md §1), under the stream's lock, written by its holder only. Rewritten whole after each message's log line is synced (temp file, fsync, rename, fsync of `chat/`), so the log is never behind it. Loaded at start, never rebuilt (§3.2, §7 mistake 3). On load its lines must tile `[0, T′)` with `T′ ≤ T`, every merged line built; `T′ < T` (a crash between the two writes) appends the missing messages; missing, unreadable or illegal, the view is rebuilt from the log once, reported, and saved (a reader without the lock rebuilds for itself and writes nothing). The reference ignores the file.
- **Render:** `<chat>\n` + `id+n|text` lines with newlines turned into spaces + `\n</chat>`. Unbuilt lines show `(not summarized yet: zoom it)`.
- **`settle(signal)`:** resolves when every view line is built. A turn waits on it before rendering (docs/optchat.md §6).

**Streams (E3).** Each writer gets `streams/<device>/` with its own `chat/`, lock and pump. In v1 only `mini` exists. In offline mode (M6) each stream's owner compacts only its own tree, and every view appends the other streams' folded views read-only as `<chat who="macbook">` blocks, as Intrepidus does.

## Engines

Every model call goes through one of three engines. The compactor and the captions choose per call from a failover chain; a master turn runs on the engine of its chain its messages name, the chain's first when they name none (E4). Because each turn starts fresh from the view, any engine can take any turn; memory doesn't care who wrote what.

```ts
interface TurnEngine {
  run(input: { view: string; texts: string[]; device: string; signal: AbortSignal },
      out: TurnEvents): Promise<TurnResult>;   // TurnEvents: talk, tool, echo, replay, usage
  steer(text: string): void;                    // mid-run message
  prime?(view: string): Promise<void>;
}
interface CompactEngine {
  summarize(job: Job): Promise<string>;        // job: context lines, step block, level
}
```

(With Effect these become services returning `Effect`s; interruption replaces `signal`. As built, `steer` is gone too: the session offers mid-run messages on the call's input and the engine reports each one it took, `src/turn/engine.ts`.)

| Engine | Auth | Used for | Notes |
| --- | --- | --- | --- |
| `claude-code` | My Claude Max login, in the unmodified `claude` binary on each device | Main turns (Opus, high effort); spare compactor capacity (Sonnet, medium) | Exactly the reference's mechanics (ref §4–§7). Never read or reuse its OAuth token elsewhere |
| `openai-plan` | Sign in with ChatGPT, "Use your ChatGPT plan" scope, ChatGPT Pro | Compactor (Luna, Sol); master fallback (Sol) | OAuth 2.0 + PKCE; the first sign-in sends `client_id=dynamic_agent_client` and gets this install's own client id back, which is saved and used from then on; Responses API with `stream: true`, `store: false`, cached as E26 says (see "Compactor calls") |
| `api-key` | Anthropic and OpenAI keys with a monthly budget | Overflow only | Our cache layout (E26): a mark at each view cut (at most 3) plus the request end, 5-minute entries only, nothing to configure |

**Refs.** A chain's entries (`engine:model`; `api-key:<provider>/<model>`) are decoded once, with the settings, into typed refs (`src/config.ts`), so a ref no engine takes is a configuration error at startup and nothing after that parses one again. `src/engines/registry.ts` is the one place that turns a ref into a turn or compactor engine. The ChatGPT plan's client and the API keys' clients are built on first use, so a server whose chains name neither engine never builds them.

**Failover** (the compactor's and the captions' chains; the master doesn't fail over, see below). Move to the next engine in the chain on a usage or rate limit, on `429 subscription_sharing_usage_limit_exceeded` from OpenAI (also when it ends a stream as `response.failed`), when `openai-plan` is signed out or not eligible (`403 subscription_sharing_user_not_eligible`, or a 401 that one token refresh doesn't cure), when the device is offline, or when Anthropic is overloaded (`529 overloaded_error`: Claude Code's error result or its synthetic message says `overloaded`, an api-key call gets the 529). An overload is transient, and a retry a few seconds later might go through on the same plan, but E4's point is to keep chatting: the next engine answers now, where a failed call would leave the node or caption to wait. For the master an overload, like any usage limit, stops the turn until it is resumed, and resuming on the same engine is the retry. Never on a refusal or a model error: those are reported, as in ref §5.2. Each failover is logged to `usage.jsonl` and shown in the UI.

**Mid-run messages on `openai-plan`.** The reference relies on Claude Code delivering stdin messages between tool calls. On the Responses API we run our own tool loop, so a steered message is appended after the current tool results, before the next request.

**Tools on non-Claude engines.** Claude Code brings Bash, Read, Edit, Write, Glob, Grep, WebFetch and WebSearch. A Sol turn gets the same set, implemented by the device runner, plus zoom and date. Its first version (M5) ships read-only tools only, so a fallback turn can answer but not change files.

**The master picks no engine by itself (E4).** Each message names the engine of the master's chain it is for (`forwardedProps.engine`, a ref, decoded by the `/ws` schema): the composer's model picker or the REPL's `/model` when it was sent. One that names none (an older client, a piped REPL) or a ref the chain lacks (said in an `info`) is for the chain's first. The chain is the list the pickers offer, labelled for people ("Claude Opus (Claude Code)", "GPT-6.1 Sol (ChatGPT plan)", `engineLabel` in `src/wire.ts`). The picker is client state only (the web app keeps it per browser in `localStorage`, the REPL per process): switching sends nothing. Why no automatic failover: the plans are paid separately, and which one pays is the user's call; a turn that quietly moved to the API key or the other plan spends what the user meant to keep. Switching engines costs a cold cache: each plan caches on its own side. Priming and the warm process (E18) follow the engine of the most recent turn, the chain's first before any (`src/master.ts`); one marked down is not primed.

**A turn stopped by a usage limit or an offline device** (or an overload) waits for a resume. Refusals and model errors still end the turn as below.

- **The stop.** What the turn logged stays, once; text it streamed and never logged is dropped; what its call never took is held again. No call accepts mid-run messages while it waits: one sent meanwhile is held (it can be taken back; a cancel logs it unanswered). Then, in order: the state says phase `needs-model` with `stopped: {ref, label, why}`; the run ends with the reason (`RUN_ERROR`); the data dir is committed. No `info`: clients show the stop once, from the state (the web app's alert, the REPL's list), never as a chat error.
- **The resume** (`{"type":"resume","engine"}`: the alert's "Try X again" or "Continue with Y", the REPL's `/resume`) is the one model frame a client sends, only in `needs-model` and only while connected. The composer's picker never resumes. One with no turn stopped, a second one for the same stop, or one on a ref the chain lacks gets an `info`.
- **What goes on.** The held messages for the stopped engine, up to the first for another engine or device, go to the engine resumed on and join its call (`handOver`, `steerIn`). The rest keep their engines: with `[m2(B), m3(A)]` held after a stop on A, a resume on B joins m2 (B's already) to the call, and m3 keeps A for a turn of its own, which may stop again. The resumed run has its own run id (`<first>+<n>`); an `info` ("Claude Opus (Claude Code) stopped (usage limit: …); GPT-6.1 Sol (ChatGPT plan) carries on from the 2 logged entries", or "tried again") is the record. The engine gets the same view and texts, what was logged so far as `earlier` (under a note that another engine, or this one earlier, began the turn), the pictures of mid-run messages taken before, and the untaken messages on `mid` (E16). Its usage record's `failoverFrom` names the engine that stopped.
- **Down marks.** An engine that hit a usage limit shows as unavailable in the pickers, with why, until it answers or `MASTER_DOWN_FOR` passes; the stopped one can always be tried again. A limit is learnt only from a failed call: a signed-out engine shows as available until a turn tries it.

## Turn and priming

The `claude-code` turn is ref §4–§6 unchanged, except for the cache TTL (E6), where the process runs (E7), that it never waits for priming (E17), and that its process may have been started ahead (E18).

1. Wait for `settle()`; on cancel, log the queued texts as unanswered `user` messages.
2. Render the view **before** logging the new messages.
3. Stop any priming still in flight, without waiting for it; never prime first (E17).
4. Log each queued text as `user`, then spawn the master on the chosen device: the base flags of ref §4 plus `--mcp-config` and `--replay-user-messages`. On the Mini this is usually the warm process started for exactly this spawn (E18).
5. Send one user message: the view cut into up to 4 blocks at 50k / 80k / 100k characters, **no cache marks**, then the texts joined by a blank line.
6. Map stream events to the log as in ref §5.3: text → `talk`, tool_use → `tool`, tool_result → `echo` (capped at `CAP`), later replays → `user`. Never log thinking. Nor an assistant message of model `<synthetic>`: that is Claude Code's own, how it reports an API error (`Claude AI usage limit reached|…`, `API Error: 529 …`) just before its error result, not the model's reply. Its text joins the result's in the failure, so a limit it names fails over (E4) even when the result line doesn't say so, and it never reaches the next engine's opening message.
7. Kill the process at the first `result`; requeue mid-run messages that were never replayed. Commit the data dir. The session reports `idle` only once the commit is done, and a message that arrives while the loop winds down starts it again.

As built, where we differ from ref §5.2:

- A refusal or an `is_error` result ends the turn like a crash: mid-run messages the call never took are logged as unanswered `user` messages, where the reference requeues them after any `result`. A refused or failed call says nothing about the next one, and the user sees the messages and the error together. A usage limit or an offline device is not this: the turn waits for a resume (Engines, E4).
- A cancel before the run starts (while waiting for summaries) logs the queued texts unanswered, each after its captions (at most `media.captionWait`), since a marker is never logged without that wait. There is no wait for priming to cancel (E17).
- A blank message is ignored: it starts no turn and logs no empty `user` entry.
- Every message waits in one inbox (`src/session.ts`) until it is logged, with the id its client sent it with, and has one owner at any moment: held for the next turn, picked by the turn that is logging it, or offered to the running call. A call reads what it is offered from its own queue and reports each message it took (claude-code: its replay; our tool loop: when it joins the next request), and the session logs it then and acks that client id; what the call never took is held again when it ends, on the call's device unless it was sent for another. The inbox holds the offered messages first, then the held ones: nothing is offered once anything is held, so the log keeps the order they were sent in. The engine a stopped turn is resumed on is offered the untaken ones first, and is given what the turn logged so far (`earlier`) read from the log. Acks never match by text, so two clients sending the same text each get their own entry. The session state lists the whole inbox as `pending` (`{clientId, text, engine, queued, media?}`, in the order sent, held, picked and offered alike, while waiting for summaries or between turns too; `queued` is true for a held one, `media` its attachments as stored), so a client that reconnects can tell a message the server holds from one the dead socket lost, by its client id. Writing a message to the log and taking it out of the inbox is one uninterruptible step, so a cancel never logs it twice.
- A turn runs on the engine of the first held message. It takes the held messages from there up to the first one for another engine, or for another device than the first of them that names one, together; that one waits for the turn after, which runs there, with everything sent after it. The turn runs on that device (the one a message was sent for, by `/on` or the composer's picker, or for a message a call never took, that call's device), else on the default device: never on one named only past the cut. The device and the messages are read together, after the wait for summaries, so a message sent during that wait for another device gets a turn of its own. A message sent for another device or engine than the running turn's therefore is not offered to its call; it waits, and so does every message sent after it, also one for the running device and engine, so the log keeps the order they were sent in.
- **Follow-ups: steer or queue.** What a message sent while a turn runs does is a session setting, `followUp`, shared by every client (T3 Code's "Follow-up behavior"; `master.followUp` in the config until a client chooses): `steer` (the default) offers it to the running call, `queue` holds it for the next turn. A message may ask for the other (`forwardedProps.followUp`: the composer's second button or Mod+Enter). A queued message is held, so the inbox keeps its order: a message that steers takes the held ones before it into the call (`steerIn`, `src/inbox.ts`), never past the first held one for another device or engine. Messages sent while the turn waits for summaries join its batch; ones sent while it waits for captions, logs its batch or waits for a resume steer or wait once a call runs.
- **Take-back.** A held message (queued, between turns, while summaries are awaited, or while a stopped turn waits for a resume) can be taken back by its client id, by any client: one user, one shared queue, so the phone can take back what the laptop queued. It it leaves the inbox and every client is told (`taken-back`, with its text and attachments, so the client that asked puts it back into its composer); it is never logged. A turn picks its batch, and so takes those messages beyond reach, in the same synchronous step that reads the inbox, before it waits for their captions; a take-back that comes later is refused ("too late: the model has it") and the message is logged and answered once. An offered message can't be taken back: the call may already have read it. A turn whose whole batch was taken back while it waited for summaries doesn't run.
- Our tool loop leaves no `tool` entry without its `echo`: a call whose request failed after it streamed, or whose turn was cancelled, is answered with `not run: <why>`, as a call of the last allowed request is. If the log refuses mid-stream, the request is read to its end anyway (it is paid for), its usage is recorded, and then the turn fails with the refusal, reported once.
- Known: a cancel that comes while the loop winds down (the commit, the check for a newer message) does not stop a restart that a message sent meanwhile causes; the new turn runs and can be cancelled in its turn.
- After the loop stops on an error (the log refuses, a defect), the messages it stopped on wait for a newer one, so a defect can't restart it forever; a message that comes in while the loop winds down is newer and starts it again.

The system prompt is MASTER + VIEW_DOC + `instructions.md`, built once at startup and sent inline as `--system-prompt` on every call and device (no file), byte-identical across them: no dates, cwd or git status (docs/optchat.md §5, §7 mistake 10). The text is the earlier gist's (E24). MASTER keeps the reference's D5 and D10 edits until subagents land (M7).

**Priming.** As ref §6: a call with the master's exact flags plus `DISABLE_PROMPT_CACHING=1`, carrying the same view blocks with our own marks, killed at `message_start`. It runs only while the session is idle: in the background 1 s after the view settles, and when a web client connects, since a message usually follows. That idle priming is what makes turns warm. A turn never waits for it (E17), where ref §6 has the turn await it (docs/optchat.md has no priming and sends no keep-alive pings, §3.3):

- The same view was primed within `PRIME_MAX_AGE`: the turn reads it from the cache.
- A priming is in flight: the turn starts at once and the priming is stopped (its fiber interrupted, its `claude` killed; it logs no usage and reports no failure). Its request would race the turn's own, which writes the same prefix anyway, so letting it finish would write the view twice; killed before `message_start`, and often before its request leaves `claude`, it costs less or nothing (whether a request killed after it was sent counts against the plan is still open, see M1 below). The next idle priming writes the marks for the next view.
- Nothing was primed: the turn just runs, and its own request writes the cache, with Claude Code's mark at its end rather than ours at the view's cut points; the idle priming after the turn writes those for the next view.

Measured on claude 2.1.289 with Sonnet and a small view: a turn sent while its view was being primed showed "priming" for 2.6 s (a fresh `claude -p`: ~1.3 s to boot, ~1.2 s to `message_start`) before its own ~2.0 s to the first text. Waiting can't shorten the time to the first token; it only spares one cache write, which on the plan is quota, not latency. So the session has no "priming" phase any more: a turn is `waiting` (for summaries) or `running`.

**Warm processes (E18).** Most of a turn's first second is `claude` booting: spawned and sent a message at once, it reaches `system/init` in ~1.3 s; started ahead and idle on stdin, in ~0.1 s. So the Mini's Runner (`src/claude/warm.ts`) keeps one process started ahead for each of the next two spawns, the master's turn and its priming (which differ only by `DISABLE_PROMPT_CACHING=1`). The engine names them when the session starts and whenever it goes idle. A spawn byte-identical in args, env and cwd gets the warm process and a replacement starts at once in the background; any other spawn starts fresh. The rules:

- At most one process per spawn, and only for the two spawns named last. The session names those of the engine of the most recent turn (the chain's first before any, E4), on the default device, and only that engine warms again after a transport move; a failover link's turn, a turn on another device and one in another folder start fresh. When the two spawns change (that engine's model, the device's MCP transport), the stale processes close.
- One that dies while idle is noticed (its output closes), never handed out, and replaced after `WARM_RETRY`, at most `WARM_TRIES` times in a row, so a broken `claude` doesn't restart forever; one that fails to start counts the same. A spawn that starts it fresh again gives it `WARM_TRIES` more.
- Each spawn has a keeper fiber that starts its process, holds it in a one-process slot and waits until it is taken, dies or grows old. A caller takes it out of the slot and ties it to its own scope in one uninterruptible step, so an interrupted caller can't leave it running.
- One older than `WARM_MAX_AGE` is replaced, so no turn runs on the login, settings and feature flags a process read hours ago. Claude Code may also update itself between a process's start and its use; that turn runs on the version it started with, which is accepted (a version change costs one cache rewrite anyway, ref §16.8).
- Every warm process belongs to a scope under the server's: shutting down kills them all, like any running turn.
- Other devices (RemoteRunner), the compactor (8 jobs at once, not worth it) and the API engines spawn on demand.

Each idle `claude -p` holds about 200 MB, so the Mini keeps ~400 MB for this. It also opens its MCP connection to `/mcp` at boot, so a turn doesn't wait for that either. Measured with `dev/latency.ts` (same machine, 3 turns each, 8 s idle between them): the median time from send to the first assistant text went from 1,990 ms to 1,160 ms, and to `RUN_FINISHED` from 3,125 ms to 2,218 ms.

**Cache TTL (E6).** The reference forces 5-minute entries (`CLAUDE_CODE_PROMPT_CACHE_TTL=5m`) to follow the earlier gist. docs/optchat.md §3.3 now leaves Claude Code subscriptions their own 1-hour lifetime. On the Claude subscription (`claude-code` turns, compactor calls and priming), and only there, we keep Claude Code's default 1-hour marks instead, and priming writes `ttl: "1h"` marks. Every mark in a request then has the same TTL, which avoids Anthropic's ordering error (1-hour entries must precede 5-minute ones). Reason: on the plan there's no per-token bill, and phone chats with gaps over 5 minutes would otherwise rewrite the whole view on almost every turn. The variable is set per spawned process; my normal Claude Code settings stay untouched. An API key is billed per token, so its requests keep docs/optchat.md §3.3's 5-minute entries with nothing to configure: the old `cache.apiKeyTtls` is gone, and a config that still has it loads with the key ignored, as the schema drops any unknown key.

## Compactor calls

The compactor's input and retries follow the earlier gist and ref §7 on every engine (E24; docs/optchat.md §4 has a compaction view, the turns' system prompt, a ruler and another retry text); only the transport changes (E5). The level of the node picks the engine chain.

**Input, all engines.** System prompt = `compact.txt` (the earlier gist's COMPACT, verbatim). Context = `<chat>` + the bare view lines (no ids) up to the node's stretch + `</chat>`, cut at the same 50k / 80k / 100k marks as the master. Step block = "For scale, this line is exactly 512 bytes:" + `SCALE` + the instruction + the message or the two child lines.

**Size retries.** In the same conversation: "That line is N bytes; the limit is 512. It must end where it is cut here:" + the line cut at 512 bytes + `| ← LIMIT`. Up to `TRIES`; keep the shortest try.

**`SCALE`.** Our own hand-written line of exactly 512 bytes, tagged `user:` / `talk:` / `tool:` / `echo:`, about a plausible session. Not copied from either implementation. A test checks its length.

Per engine:

- **`claude-code`:** exactly ref §7 (layout A, `--safe-mode`, `DISABLE_PROMPT_CACHING=1`, our 4 marks). TTL follows E6.
- **`openai-plan`:** Responses API, one request per try, the full input re-sent each time (`store: false`). Cached as the earlier gist had it for the Responses API (E26), on every request of every engine that speaks it (this compactor, the api-key OpenAI one, and our tool loop as master): `prompt_cache_breakpoint: {mode: "explicit"}` on each context (or view) piece that ends at a cut, the same in every request; the request end cached implicitly (`prompt_cache_options` left at its default); `include: ["reasoning.encrypted_content"]`, and every reasoning item a reply holds sent back verbatim in the next request (the next tool round, or the next size retry), ahead of what followed it; `reasoning.context: "all_turns"`, so a mid-run message doesn't drop the earlier reasoning and miss the cache. A model that answers 400 naming `prompt_cache_breakpoint` (the reference measured the Codex route doing that for `gpt-6.1-sol`) gets the same request again without it, and none from then on, which is reported once; it then caches only what OpenAI caches implicitly. The route rejects `system` messages, so `compact.txt` goes into `instructions`, as OpenAI's docs for the route say. Each try is one user message of input-text parts (the context pieces, then the step), and a retry appends the previous reply's output (its reasoning items and its text as an `assistant` message) and the retry text as a new user message.
- **`api-key`:** Anthropic gets the context pieces first with a 5-minute mark at each cut (at most 3), the step after them, and the top-level automatic `cache_control` on every try, so a size retry reads the whole try before it (the compactor calls share their `<chat>` prefix too); OpenAI is the same as `openai-plan`.

**Bake-off (M3).** Before fixing the level cutoff, replay ~500 real messages through Luna, Sol and Sonnet compactors and compare:

| Measure | How |
| --- | --- |
| Retries per node | Mean and p95 tries until ≤ 512 bytes |
| Cost per message | From `usage.jsonl`, in dollars or plan share |
| User's words kept | How often a quoted user sentence survives 2 and 3 levels up |
| Findability | Questions generated from raw messages; an agent with only that tree and zoom must find the answers |

## zoom and date over MCP

The server exposes `zoom` and `date` as an MCP server at `/mcp` on the tailnet, so a `claude -p` on any device reaches the same memory (E8, replacing the reference's stdio server, D8).

- **Transport:** a WebSocket by default, one JSON-RPC 2.0 message per text frame each way (`GET /mcp` that upgrades); also one message per `POST /mcp`. Claude Code documents only `stdio`, `sse` and `http` for `--mcp-config`, but its config schema also takes `{"type": "ws", "url", "headers"?}`, and it connects with subprotocol `mcp` and no `Origin` (probed on 2.1.289: connected, and a real turn called `zoom` over it). A warm process (E18) opens the socket at boot and keeps it, so a turn's tool calls go over a connection already open. Because the type is undocumented, each device falls back by itself, and while on ws watches every `claude` there (priming usually comes first) for one of these: its `system/init` lists `optchat` as `failed`, or leaves it out (2.1.289 skips an entry whose type it doesn't know, with a warning on stderr only when that is a terminal); or it ends before any `system/init` because its config was rejected (Claude Code checks `--mcp-config` against its schema as it starts and exits with `Error: Invalid MCP configuration:` on stderr; 2.1.42 does that for any entry its schema refuses); or it ends before `system/init` twice in a row for any reason. `pending` and `needs-auth` say nothing about the type and change nothing. That device's calls then use the `http` form, the user is told once (in words that allow for the other cause of `failed`, a server it couldn't reach), and its warm processes (E18) are started again with the new config by the engine the warm processes follow (another link's move leaves them to the session's next warm, when it goes idle). A rejected config counts only when the error names `mcpServers.optchat`. `server.mcpTransport: "http"` turns ws off. Which transport is used changes nothing the model is sent, so not the cache either.

- **Behaviour:** exactly ref §9 and docs/optchat.md §6, with its tool descriptions verbatim. `zoom(id, n)` validates integers, `n` a power of 2, `id % n == 0`, `id + n ≤ T`, the node built; otherwise `No line id+n.` `zoom(id, 1)` returns `id+0|kind: text` in full and works for any existing message; on a user message with attachments it also returns their pictures as MCP `image` content (E20, see Media). `date(id)` returns local time as `2026-10-04 14:03`, or `No message N.`
- **Read-only:** answers from the server's in-memory tree; never takes the lock.
- **Cache stability:** the `--mcp-config` JSON is the same for a device's priming and real turns. The server name stays `optchat`, so the tool names (`mcp__optchat__zoom`, `mcp__optchat__date`) and the cached tool list are the same on every device; only the URL differs, and the URL isn't sent to the model.
- **Auth:** a `claude` on another device calls `/mcp` at `server.publicUrl`, that is through `tailscale serve`, which hides the caller's address and adds its owner's login. So WhoIs plays no part: the guard is the secret key in the URL (made at startup, sent only inside `--mcp-config`) plus the `allowedLogins` check every route has. Over either transport: the WebSocket's upgrade request passes the same Host, Origin and login checks as any request (`server/auth.ts`) and needs the same key. A `claude` on the Mini calls the loopback URL with the same key. Without `server.publicUrl` the server refuses turns on other devices rather than hand them a loopback URL and its key.
- **Offline mode (M6):** gains `who`, plus `grep(regex, who)`, as in Intrepidus.

## Multi-machine

One chat, one memory, two pairs of hands: the Mini keeps memory and the turn loop, and runs each turn's `claude -p` on whichever machine has the files (E7). The MacBook needs only `claude` logged in and the device runner.

**Device runner (`device/`).** A small Bun daemon, launchd-managed, listening on the tailnet only.

- `GET /spawn`, a WebSocket whose first frame carries the args, env and cwd; then stdin goes in and the stream-json events come out, and a last frame says how `claude` exited (`src/claude/wire.ts`). It refuses a cwd outside the configured folders, after resolving symlinks and `..`, and any env but `CLAUDE_CODE_PROMPT_CACHE_TTL` and `DISABLE_PROMPT_CACHING`, the two a turn and its priming set. It only ever runs the `claude` binary, never a shell, but the caller chooses its arguments: these checks keep turns alike across devices and are not a sandbox. The boundary is who may call: only the server's device (`OPTCHAT_SERVER_DEVICE`, else `defaultDevice`), by Tailscale WhoIs.
- Kills children on disconnect, on SIGTERM and after `KILL_GRACE`, mirroring the reference's child registry (ref §5.2). Each `claude` runs in its own process group, so the kill reaches the commands it started. A daemon killed with SIGKILL (launchd stops it with SIGTERM) leaves its running children behind, for the same reason; not prevented.
- Listens on the machine's `tailscale ip -4` address only. MagicDNS also answers AAAA, so the server resolves a device's name to IPv4 before connecting.
- Writes nothing of its own; the master's tools change files on that machine, nothing else.
- `POST /tool` runs one read-only tool (Read, Glob, Grep) for a turn on an engine with its own tool loop (M5): a `ToolCall` in, a `ToolReply` out, let in on the same terms as `/spawn` (no `Origin`, a trusted node). Every path is resolved (`~`, `..`, symlinks) and must land in the folders; Glob patterns may not climb out; output is capped at 100k characters and each call at 30 s. Grep's pattern is the model's and a JavaScript regex can backtrack without end, so the search itself runs in a Worker (`src/tools/grep-worker.ts`) that is terminated when the call times out or is interrupted; the server's event loop is never the one blocked. No shell and no write. The server's own device runs the same code (`src/tools/files.ts`) in-process.
- `GET /health` returns the `claude` version, so the server can warn when devices differ (a version change invalidates the cache once, ref §16.8). `/api/devices` shows each device as online, offline, or refused (it answered 403: its callers or the server's node name are misconfigured).

**Routing.** Each turn picks a device: an explicit picker in the UI, a `/on macbook` prefix, or the default device. The choice is stored as an extra `device` field on that turn's log entries, which readers ignore, as pi-optchat does with its `origin` field. The user's text is never changed; the tool calls' paths already show the compactor where work happened.

**Device offline.** The turn fails fast with a clear notice in the UI and in the log; the failover chain may then run it on another engine with read-only tools. Never queue silently. The server remembers an unreachable device for 5 s, so a priming and the turn right after it wait for it once and report it once.

**Offline mode (M6).** If the Mini is unreachable, the MacBook runs a local server on `streams/macbook/` and pushes to the shared git remote. The Mini pulls before each turn and shows that stream read-only. Two streams means two chats until the user merges them; that is accepted, as in Intrepidus.

## Server, WebSocket API and CLI

The reference's session object (`createSession` in ref `turn.ts`) moves into the server unchanged; the REPL and the web UI become two clients of one WebSocket API (E1).

**Server.** `Bun.serve` on `127.0.0.1:7700`, published to the tailnet by `tailscale serve`. Routes, one module each under `server/routes/`: `/ws` (the API), `/mcp` (zoom and date), `/api/*` (read-only JSON for the browser and stats; `/api/assets` takes uploads, see Media), `/` (the built web UI). `server/app.ts` builds the parts (chat, compactor, engines, session) and hands them to the routes; `server/placement.ts` says where each device's turns run.

**Protocol: AG-UI events (E15).** The WebSocket carries AG-UI protocol events, a standard any AG-UI client can read. Both ends are ours: the server in Effect, the web UI's session store over the same events (see Web UI). Any number of clients watch the same server-owned turn. The state the events carry and the JSON of `/api/*` are schemas in `src/wire.ts`, a module with no node imports that the web UI bundles too; the server takes its types from there and encodes each `/api/*` body through its schema.

| What happens | AG-UI event | Notes |
| --- | --- | --- |
| Client connects or reconnects | `MESSAGES_SNAPSHOT` + `STATE_SNAPSHOT` | The last window of log entries and the current state; mid-run also `RUN_STARTED` and the reply streamed so far, so a client that joins mid-reply gets all of it |
| A turn starts | `RUN_STARTED` | `threadId` = stream name (`mini`), `runId` = the turn's first `user` entry |
| A `user` entry is logged (also mid-run, also from another client) | `MESSAGES_SNAPSHOT` delta or a user text message | So every client sees every message |
| Live reply text, then the `talk` entry | `TEXT_MESSAGE_START` / `CONTENT` / `END` | Message id = the entry's log index `i` |
| A `tool` entry | `TOOL_CALL_START` / `ARGS` / `END` | Tool name and JSON input |
| An `echo` entry | `TOOL_CALL_RESULT` | The capped text, as logged |
| Waiting for summaries, running, device, engine, view size, follow-ups, the models | `STATE_DELTA` | One shared state object (`SessionState`, `src/wire.ts`); each `pending` message says the `engine` it is for, whether it is `queued` (held, so it can be taken back), and carries its attachments (`media`, as stored) when it has any; `followUp` is the follow-up setting; `engines` the master's chain as the pickers show it (`{ref, label, down}`, `down` why one is unavailable); `stopped` the engine that stopped a turn waiting for a resume (phase `needs-model`), and why |
| Usage records, failovers, errors, refusals, device offline | `CUSTOM` (`usage`, `info`) | Shown in the status line and the stats screen |
| Thinking | `CUSTOM` (`thinking`) | Token count only; thinking text is never sent |
| The turn ends | `RUN_FINISHED` or `RUN_ERROR`, then `MESSAGES_SNAPSHOT` | Exactly one per `RUN_STARTED`, also on a cancel (`RUN_ERROR` "cancelled"), after the run's own entries (a cancelled tool loop's `not run: cancelled` echoes) and before anything outside it is logged; the open reply is closed first. The snapshot resyncs every client to the log, so a reply cut off before its `talk` entry disappears before its index goes to the next entry |
| Client uploads an attachment | `PUT /api/assets`, plain HTTP, the body is the file | Not an AG-UI event: bytes go over HTTP (progress, retry by hash), the message over the socket. Answers `Asset` (`src/wire.ts`): `{kind: "image", sha, mime, width, height, bytes}`, or for a video also `duration`, `frames`, `sheet`, `transcript`, `notice`; 400 empty, 413 too big or too long, 415 not a type it takes, 422 can't decode. `GET /api/assets/<sha or 12-hex prefix>[/thumb]` serves one back, with `Accept-Ranges: bytes` and one `Range` answered (206, 416 past the end), which iOS Safari needs to play a video |
| Client sends a message | a `RunAgentInput` frame | Starts a turn, or becomes a mid-run message when a turn is running; a blank text with no attachments is ignored. Its content is the text, or AG-UI's parts: a `text` part and up to four `image` / `video` parts whose `source` is `{type: "url", value: "asset:<sha256>"}`; the server looks each up in its own store and leaves out (with an `info`) one it doesn't hold. Only user messages whose ids the connection has not sent before are taken (a client may resend the whole history); an id that is the log index of a user entry with the same text names that entry and is not new, any other id is the client's own |
| A client's message is logged, or cannot be | `CUSTOM` (`ack`: `{clientId, messageId, error}`) | Before the user entry it names; `messageId` null and `error` set when the log refused it (it stays queued for the next message, and is acked again with its index when that logs it). A client tells its own messages by this, not by their text |
| Client cancels | `{"type":"abort"}` | Same as Ctrl-C in ref §10; a client sends it only while connected, so a stale one never cancels the next turn |
| Client sends a message the other way | `forwardedProps.followUp` of the `RunAgentInput`: `"steer"` or `"queue"` | Only when it differs from the session's setting (see Turn and priming, follow-ups) |
| Client sends a message for an engine | `forwardedProps.engine` of the `RunAgentInput`: a ref of the master's chain | The composer's picker or the REPL's `/model` when it was sent; none, or a ref the chain lacks (said in an `info`), is the chain's first. Picking sends nothing |
| Client takes a held message back | `{"type":"take-back","clientId"}` | Answered to every client by `CUSTOM` `taken-back`: `{clientId, text, media, error}`, the message as it was (never logged), or `text` null and `error` set when a turn already has it or the server holds no such message. Sent only while connected |
| Client changes the session's settings | `{"type":"settings","followUp"?}` | `"steer"` or `"queue"`; may wait for the connection. Saved in the data dir's `session.json`. A `lead` (a client from before the per-message model) gets that client alone an `info` to reload. Every frame, these included, is decoded by its Effect schema (`server/routes/ws.ts` `Inbound`); one that doesn't decode is dropped |
| Client resumes a stopped turn | `{"type":"resume","engine"}` | Only in `needs-model`, and sent only while connected, like an abort (the client says when it wasn't); `engine` a ref of the master's chain. One that isn't, a resume with no turn stopped, or a second resume of one stop (two clients at once), is answered with an `info` |
| A usage limit or an offline device stops a turn | `STATE_DELTA` with phase `needs-model` and `stopped`, then `RUN_ERROR`; no `info` | No failover (E4): the turn waits for a resume. Clients rely on the state coming first, to show the stop once. The resume: `RUN_STARTED` with a fresh run id, then a `CUSTOM` `info` that is the record of the stop |

The log stays the source of truth. A client's state is only a view of it, rebuilt from `MESSAGES_SNAPSHOT` on every reconnect and after every run, so there is no replay protocol.

**CLI.** `optchat` is the reference's REPL (ref §10: bracketed paste, Ctrl-C and Ctrl-Z paths, plain scrollback) talking to the server over `/ws`. `/steer` and `/queue` typed alone set the follow-up behavior; `/model` lists the master's engines (the one this REPL's messages are for, and why one is unavailable), and `/model <n>` or `/model <ref>` sets it for its next messages, sending nothing; `/resume` retries the engine that stopped a turn waiting in `needs-model`, `/resume <n|ref>` goes on with another (the REPL lists the engines when one stops; sent only while connected). It says once when a message of its own is queued for the next turn, and when one was taken back by a client. Piped, it exits once every message it sent is answered, and non-zero when one was not: the log refused it, its run ended in an error (a refusal, a cancel), a client took it back, or a turn stopped for a resume (nothing piped can resume it). `optchat view`, `stats`, `browse` and `import-*` stay local commands that read the data dir without the lock, as in the reference.

## Web UI

A phone-first single-page app in `web/`: Vite + React 19 + Tailwind 4, built into static files the server serves (E2). One page with tabs, no router framework. It is installable as a PWA, so it opens like an app from the home screen.

Screens:

- Show what the log holds and nothing more: no thinking text, and markdown rendering never hides what the model actually wrote (a raw-text toggle per message; a tool's input as logged). Every row is keyed by its log index, from the first streamed event to the snapshot that confirms it.

- On a phone, Enter in the composer is a new line and the send button sends; on a keyboard, Enter sends. What the user typed is sent as typed.
- Opening the app triggers a background prime (see Turn and priming).
- Dark and light themes; works at 360 px wide.
- UI tests replay scripted conversations as AG-UI events with no model or network (`web/src/test/fixture.ts`, a fake server behind the link's socket). `@shadcn/helpers/tanstack-ai` was the plan, but it scripts replies to a client's own request (and pins `@tanstack/ai` 0.40), while our server pushes snapshots and turns other clients started. End-to-end tests run the real server with the fake `claude` (`web/e2e`).

## Media

Images and short videos from the phone (E19, E20). The log stays text: a message with attachments is logged as what was typed plus one marker line per attachment, the bytes live in a sidecar, and only the turn that sends them sees the pictures. hermes-optchat's sidecar was the idea; none of its code is used. Code: `src/media/` (store, normalization, video, captions, the service), `server/routes/assets.ts`, the marker grammar in `src/wire.ts`.

**Store.** `~/.optchat/assets/<sha[:2]>/<sha>.<ext>`, one store under the home for every stream, plus `<sha>.json`, the asset's metadata (`Asset` in `src/wire.ts`), written after its bytes, so an asset with metadata is whole. Shared rather than per stream because the bytes are content-addressed: two writers (M6) that store the same photo write the same file, and a git merge of two streams' assets never conflicts. The name comes only from the digest and a fixed extension table (`jpg png webp gif mp4 mov webm json`). Each file goes to a temporary name, is fsynced, renamed into place and its directory fsynced; directories are 0700, files 0600; a file already there is kept, so a write is idempotent. All of it is written while the upload is answered, long before a log line names it. persist commits it with the rest of the home and pushes it, except uploads no logged message names: a photo attached in the composer and never sent is not committed (persist writes the paths `Media.unreferenced` returns, from the log's marker lines and the frames, sheet and standard-tier copy an asset is made of, into the repo's own `.git/info/exclude` before each `git add -A`; it is never committed, and it only keeps untracked files out, so what was committed stays). Those files stay on disk, untracked, until someone removes them; a periodic cleanup of old ones is not built. Size: a standard-tier photo is ~150–400 KB, a 45 s clip its upload (up to `maxVideoBytes`, 50 MB) plus 24 frames of ~40 KB and a sheet; git keeps every committed one forever and a clone fetches all of them. **Videos are committed by persist, as uploaded** (the copy with its metadata dropped, streams as they were): GitHub warns at 50 MB and refuses a file over 100 MiB, which is why `maxVideoBytes` defaults to 50 MB. At a few photos a day that is ~1 GB a year; past that, git LFS for `assets/` or transcoding a clip to a small proxy before it is stored is the way out (neither is built). Nothing sent is ever deleted: an asset named only by a line that was compacted away is still reachable by zoom.

**Upload.** `PUT /api/assets` behind the same guard as every route (Host, Origin, `allowedLogins`). The type is read from the magic bytes, never from the client: JPEG, PNG, WebP, GIF; MP4, QuickTime, WebM. Anything else is 415 (a script named `photo.png`, SVG, PDF, HEIC). Limits: `maxImageBytes` 30 MB, `maxVideoBytes` 50 MB, `maxVideoSeconds` 180. The body is read whole (`request.arrayBuffer`), so a video is held in memory once as the upload and once as its stored copy, not three times; at most 2 uploads are worked on at once (a semaphore in `ingest`), the rest wait. Bun refuses a request body over its own `maxRequestBodySize` (128 MiB by default) before any route runs, so `serverLayer` sets it to the larger of the two limits plus 1 MiB: raising `media.maxVideoBytes` is enough. An image is decoded by sharp (libvips; prebuilt for linux-x64 and darwin-arm64, installs cleanly under Bun 1.4.2), refused past 100 megapixels, turned upright by its EXIF orientation, downscaled to the tier's long edge (standard 1568 px, the default; `?detail=high` 2576 px, the tray's "HD" toggle), and re-encoded: JPEG q85 (mozjpeg) when opaque, WebP q90 when it has transparency; the first frame of an animated GIF. sharp writes no EXIF, GPS, ICC or XMP. Only this normalized image is kept, never the original: it is what the engines get and what zoom returns. A `?detail=high` image whose long edge is past 2000 px also keeps its standard-tier copy, an image asset of its own named by `small`: a request with many pictures is sent that one (see Engines), and zoom always answers with it. The same upload gives the same bytes, so it is the same asset. The web client downscales first (canvas, JPEG q0.85 at 1568 px; a smaller image goes up as it is), so a phone photo is usually re-encoded twice at q85; the loss is small and not measured.

**Video.** ffprobe reads its length and streams; ffmpeg copies it without metadata (`-map_metadata -1`, bit-exact, streams copied: a phone writes where it was shot into the file), which is the stored video and its digest; frames are taken at one per 2 s, or 24 spread evenly over a clip longer than 48 s, at most 768 px on the long edge, each stored as an image asset (JPEG q80), plus one contact sheet (the frames in a grid with their times, within 1568 px) that thumbnails and zoom show. The audio is transcribed only by a local whisper named in `media.whisper` (a command; the 16 kHz mono WAV's path is appended, stdout is the transcript, capped at 8,000 characters); without one the asset says `audio not transcribed: no local whisper is configured`. Audio never goes to an outside service. The bytes are a stranger's, so every call is bounded: `-protocol_whitelist file` (no URL, playlist or concat input can make ffmpeg fetch anything), the demuxer forced from the sniffed type (`-f mov` for MP4 and QuickTime, `-f matroska` for WebM) instead of ffmpeg's guess, `-t <maxVideoSeconds>` on every read, a video whose ffprobe size is past 8192 px on a side or 8192×4320 in all is refused (413) before a frame is decoded, and a call that runs longer than `media.toolSeconds` (60 s) plus the clip's length is killed with SIGKILL (422), and whisper has its own limit, `media.whisperSeconds` (120 s) plus the clip's length (it loads a model before it decodes, so a minute is too tight for a big one; a whisper killed this way is only `audio not transcribed: whisper failed: it took longer than …`, the upload goes on). A whisper that hangs holds one of the 2 upload slots until it is killed, up to `whisperSeconds` plus the clip's length (5 minutes for a 180 s clip), and the other uploads wait; it is not run outside the slot because it reads the audio from the upload's temporary folder and its transcript goes into the asset's metadata, written last, so it belongs to the one ingest; a tool that exits non-zero is 422 too. ffmpeg and ffprobe must be on the server's PATH (or `media.ffmpeg`, `media.ffprobe`): this box has them, the Mini needs `brew install ffmpeg`. Images don't need them.

**Markers.** One line per attachment after the typed text (none when the text is blank), at most 4 per message (more are left out with an `info`; the web tray stops at 4):

```
[image 9d0c38e7aafe 1568x1176 212KB: a whiteboard with three arrows from Queue to Turn]
[video 4be1c09f2d73 47s, 24 frames: a cat jumps onto the desk and knocks over a cup]
```

The 12 hex digits are the digest's prefix, enough to find the asset (`GET /api/assets/<prefix>`, zoom); the caption is one line of at most 120 bytes (the model is asked for 100 characters; a longer one is cut between code points, never inside a surrogate pair, and ends in `…`) with brackets turned into parentheses. A marker is then at most 160 bytes (`[image 9d0c38e7aafe 2576x2576 30720KB: ` and a 120-byte caption), a typical one ~100. One marker with the text beside it is well inside a node (512 bytes); four typical ones fit with ~100 bytes for text; four with the longest captions (640 bytes) do not, so that message is summarized by the compactor instead of shown whole, which is why a test checks that the summary's input keeps every sha. Only trailing lines of this shape count (`splitMarkers`); one typed mid-message is text. The compactor's prompt is unchanged: it sees markers as part of the message (a test checks that the input of a marker-only message holds every sha); whether summaries keep them is for the bake-off.

**Captions.** A chain like the compactor's, `media.caption`, default `["claude-code:haiku"]`: `claude -p --safe-mode` with no tools and `prompts/caption.txt` as its system prompt, one stream-json message with the image block and the ask; api-key and openai-plan links go through their provider (the plan only with `planImages`). Usage records have role `caption`. A video is described from its sheet and the start of its transcript. Timing: the caption starts as soon as the upload is stored, in the background, usually long before the text is typed; the session never writes a marker without having waited for its caption, at most `media.captionWait` (10 s) each, then logs it with the caption or `(not described)` if none came. That is one rule in one place: `logMessage` awaits the message's captions before it writes, and each message asks for them once (`captionsOf`), so what the log keeps and what an engine is sent come from the same answer. A turn waits for the captions of exactly the messages it is about to log, together; a message that arrives meanwhile is not in that batch: it is offered to the call as soon as the run starts, ahead of anything sent later (unless it, or one sent before it, is for another device: then it waits for the next turn, see "Turn and priming"), and waits for its own captions there (a test sends photo A and photo B quickly and checks both markers carry their captions; another checks a message sent during that wait is logged before one sent during the run). A mid-run message is offered to the call after its captions are in, and logged when the call takes it with the same ones. The line is written once and never patched, so the append-only log only ever holds what was known when it was written. Rejected alternatives: a placeholder plus a later `note` entry would put a second leaf in the tree for every picture and split the description from its message in every summary; not waiting at all would log most markers undescribed. A caption call that fails is reported once and retried for the next message that names the same asset.

**Engines.** The sending turn gets the pictures after the view blocks and before the texts, so the view's cache prefix is unchanged: `claude-code` as stream-json `image` blocks with a base64 source (the shape in the Agent SDK's streaming-input docs; checked against the input schema in the installed claude 2.1.289's bundle, which takes `{type: "image", source: {type: "base64", media_type, data}}`, not by a model call), Anthropic api-key as `image` blocks, the Responses API as `input_image` with a data URL. Every picture follows a text naming it, so the model can match pictures to markers: `image <sha12>:` before an image, `video <sha12> at 0:14:` before each frame of a video, then the video's transcript or why there is none. Mid-run messages carry theirs the same way: one function (`forEngine`, in `src/session.ts`) builds the text and pictures of the opening message and of each mid-run message, from the awaited captions. After a failover the next link's opening also carries the pictures of the mid-run messages a link before took (the session keeps them for the turn), after the opening's own and against the same budget: those messages reach it in `earlier`, by their text and marker lines only, so without this it would see a picture's marker and never the picture; an engine not sent images gets the note instead.

**Picture budget** (`src/media/budget.ts`). Anthropic takes at most 100 images in a request, and with more than 20 none may be over 2000 px on a side; a turn's request grows as it goes. Each call of an engine has one budget, asked for every batch of attachments in one place (`forEngine`): the opening message's, then each mid-run message's. The attachments of one call take at most `MAX_ATTACHED` (60) of the 100; the other 40 are left to the pictures the turn's tools add, zoom's answers (at most 4 each) and Read of an image file, which nothing counts: the MCP server doesn't know which turn asked, and Claude Code's Read is its own. 40 is ten zoom answers, more than a turn uses, so a request no longer passes 100 when a turn full of video frames zooms or reads. (With 8 kept for zoom, as first built, four videos took 92 and three zooms broke the request with a 400 mid-turn.) Zoom's own pictures are always ≤ 2000 px (a high-detail image answers with its `small` copy). When a batch doesn't fit, video frames are thinned first (the same count for every video, a short clip keeping all its frames, spread evenly with the first and last in), then, when that would leave a video fewer than 4 frames, each video is shown as its contact sheet, then the first attachments in the order sent keep one picture each (an image whole, a video its sheet) and the rest are markers only, with a line saying so. A request that could pass 20 images with `ZOOM_RESERVE` (8: two zoom answers) added (or that already holds one over 2000 px, and so must stay at 20, its attachments at 12) sends every image at ≤ 2000 px: a high-detail image goes as its `small` copy. Known: a turn whose request holds a high-detail image at full size and whose tools then add more than 8 pictures passes 20 with a wide one, and the API refuses it; only `?detail=high` uploads, which have no UI yet, can cause it. Test: 4 videos and a high-detail image share 60. The same pictures go to `claude-code` and to the tool loop (Anthropic, Responses), since both get them from the session. An engine that is not sent images (openai-plan unless `media.planImages`; any engine whose `vision` is off) gets the marker lines and a note saying so, also after a failover and mid-run. Later turns see only the markers, since history is the memory; Claude Code runs a fresh process per turn (E18 hands out a process that has seen no message), so no image lingers in its context.

**zoom (E20).** `zoom(id, 1)` on a user message answers with its text and, per marker (at most 4), the image (at most 2000 px: a high-detail image answers with its standard-tier copy), or a video's contact sheet after a line with its frame count and transcript; a missing file is said in text. Same over HTTP and WS; the tool list is byte-identical. Our own tool loop's zoom (M5) stays text only: function-call outputs with images are not wired.

**Web.** The composer has an attach button (`accept="image/*,video/*"`), a separate camera button (`capture="environment"`, not Baseline, hence two), paste and drag-and-drop. Each file shows in a tray with its preview (an object URL of the file itself), its upload's progress (XMLHttpRequest; fetch has none) and its error, and can be removed (a file removed, or a composer closed, while its photo is still being downscaled is never uploaded). Uploads start at once; send is on when there is text or a finished attachment and none is still uploading or failed. A logged user message shows its attachments' thumbnails from `/api/assets/<sha12>/thumb` above the bubble (a tap opens the full asset; a video plays since the server answers byte ranges) and its marker lines dimmed in the bubble. The REPL shows markers as text and can't upload.

## Tailscale, auth and operations

Nothing listens on a public interface; the tailnet is the only way in (E9).

- **Publishing:** `tailscale serve --bg --https=443 http://127.0.0.1:7700` on the Mini gives `https://<mini>.<tailnet>.ts.net` with a valid certificate. Device runners listen on their tailnet address only.
- **User auth:** `tailscale serve` adds identity headers (`Tailscale-User-Login`) to each request. The server accepts a request only if that login is in `allowedLogins` and the request came through serve on loopback; anything else gets 403.
- **Browsers:** `/ws` drives a master with `bypassPermissions`, so a web page must not reach it from someone's browser (cross-site WebSocket hijacking, DNS rebinding, or a page on the phone riding the user's own serve identity). Every route checks `Host` (`127.0.0.1:<port>`, `localhost:<port>`, `[::1]:<port>` or the host of `server.publicUrl`) and, when an `Origin` is sent, that it is the server's own origin; CLI clients send none. The threat model is written out in `server/auth.ts`.
- **Machine auth:** a device runner asks Tailscale's local WhoIs which node is calling and compares its full MagicDNS name with the server's device's, the only node it lets in (`OPTCHAT_SERVER_DEVICE`, else `defaultDevice`, as in "Multi-machine"; its URL's host plus this tailnet's suffix, so a device URL must use a name, not an IP address). Other configured devices are not let in: the server is the runner's one legitimate caller. Answers are cached per address for 10 s, and at most 4 WhoIs calls run at once. Before that it refuses any request with an `Origin` header: a page in a browser on an allowed machine is that machine's node too, and the server's runner sends none. `/mcp` is covered under zoom and date. No tokens to rotate.
- **Processes:** one launchd agent on the Mini (`optchat-server`) and one on the MacBook (`optchat-device`), each with `KeepAlive`, logs in `~/Library/Logs/optchat/`. The Mini's energy settings keep it awake.
- **Permissions:** the master runs with `bypassPermissions` (ref D9). The device's folder allowlist only sets the working directory; it does not confine `claude`, whose Bash can reach anything that user can. The boundary is who may call the runner: the server's device's node only, and no browser.
- **Persistence:** the data dir is its own git repo, committed after every turn as in ref §10, and pushed to a private remote (E10). The push is the backup and, in M6, the sync. The session turns idle once the commit is made; the push runs in the background, one at a time, and a failing push is reported once until one goes through again.
- **Secrets:** the ChatGPT plan token and API keys live in the macOS Keychain (`security`, service `optchat`), never in the repo or the data dir. Off macOS (Linux, dev) they go to `~/.config/optchat/secrets.json`, mode 0600. `$OPTCHAT_SECRETS` names such a file instead, on any machine; the tests point it at an empty one.

## Usage and cost tracking

Every model call that reports usage appends one line to `usage.jsonl`, as in the reference, with more fields (E11); a failed call gets its line too when the engine says what it cost, priced on an API key and counted against its budget. A call that fails before it reports any usage (an HTTP 429 or 5xx, a network error, no access token) gets no line: it shows only as a report, and a failover it causes as the next engine's `failoverFrom`. For a turn, `failoverFrom` names the engine a usage limit or an offline device stopped before the user resumed the turn (the master doesn't fail over, E4); the stats screen lists these and the compactor's failovers together as "Engine changes". Two weeks of these lines decide the plan questions below.

```json
{"date":"2026-10-05T04:46:00Z","role":"turn|prime|compact|subagent|caption","engine":"claude-code",
 "auth":"claude-max|chatgpt-pro|api-key","model":"opus","device":"mini","level":null,
 "usage":{"input":0,"cacheRead":0,"cacheWrite":0,"output":0},
 "cold":false,"attempt":1,"failoverFrom":null,"ms":0}
```

- `cold` is true when the call read less than half the view from the cache. For a turn it is judged on the first request's usage (`message_start`), the one that reads the view; the token counts are the whole call's. Compactor records carry the device they ran on (the server's own machine).
- `level` is set for compactor calls, so the per-level split can be costed.
- API-key calls also get a dollar figure from a price table in config; the server stops using the key when its monthly budget is spent and says so in the UI.

Expected spend, as a baseline to check against (estimates from the reference's measured token counts, not our runs):

## Milestones

Each milestone ends with `bun test` green, the parity test passing, and a short note in this doc of what was measured. M0–M2 follow the reference's own build order (ref §12); the rest is ours.

1. **M0, core parity.** Repo, Effect setup, schemas, and a one-day spike calling Bend's JS output from TypeScript. Store, tree, view, pump with a fake compactor; OptMem import; `view` CLI. Done when the parity test matches the reference byte for byte on a fixture log.
   - *Sawtooth (2026-10-08, Bend 2.0.35).* The kernel's view became docs/optchat.md's: due from the last message, `append` the sawtooth, the refold a one-off rebuild returning the view and its debt (it skips the batch for a message that keeps an owing-nothing view within `VIEW_HIGH`, or that comes while a batch is owed and makes no new pair: the tree is fixed during a rebuild). The laws gained `saw_merges`, `append_merges`, `saw_within`, `append_grows` and `saw_batch` (eighteen in all with `coords_complete` and `offers_complete`, `--verdict` too). The view is saved to `chat/view.json`; `test/view.test.ts` covers the sawtooth, a restart, a stale, missing or damaged file. `dev/cache-sim.ts` replays 30,000 messages (nodes of 300–512 bytes, all built at once) and counts the line-inputs rewritten per message, from the first line that differs from the last call's view: a fit at every message rewrites 94.4 of 315 lines (first-message due) or 94.0 (last-message due); the sawtooth 1.8 of 236. docs/optchat.md §3.3 reports about 2 per message for its batches.
   - *Measured (2026-10-05, Bend 2.0.35, Bun 1.4.2, effect 4.0.1).* `bend kernel.bend -o kernel.mjs` gives an ES module whose default export Bun calls directly: constructors cross as `{$: "Name", …}`, Nats go in as numbers and come back as bigints, and Base's arithmetic compiles to native operations. Non-tail recursion over a list overflows the JS stack between 20k and 40k elements, so every walk over a view or a log is tail-recursive (a test runs a 100k-line view). All ten laws in `kernel/LAWS.bend` check, also under `--verdict`; their vocabulary (siblings, merge, size, start, width, built-before) is defined from Base, not from the kernel's own functions. `test/kernel.test.ts` checks the kernel against a literal model of the earlier gist's rule 3 and merge order on seeded random runs, and the parity fixture (900 messages, 764 view lines) gives the same log, tree and `optchat view` bytes from both CLIs on both data dirs. Refold of a fully built tree: 0.10 s at 2,300 messages, 0.84 s at 20k, 3.6 s at 60k (the reference reports 20 ms at 2,300); 100k messages with nothing to merge: 0.15 s, since refold skips `fit` when the view is within budget or nothing in it can merge. One `fit` takes 1.2–1.6 ms and one rule-3 pass 3–54 ms. At 100k messages one pump kick costs about 290 ms of synchronous work (`offers` 117 ms, `first` 44 ms, `buildFree`'s scan for free nodes 125 ms), and the startup refold of a fully built tree 6.3 s; both are rebuilt from scratch on every call. An OptMem import writes every note, builds the free nodes, then folds the view once: 10k notes in 5.6 s, one fsync per line included (refitting after each note took 47 s).

4. **M3, ChatGPT-plan compactor.** `openai-plan` engine, per-level chains, the bake-off. Done when the level cutoff is set from bake-off data.
   - *Built (2026-10-05), not yet measured.* `optchat login openai` runs Sign in with ChatGPT: PKCE (S256), `state` and `nonce`, a one-shot callback on `http://127.0.0.1:1455/auth/callback`, the code exchanged with the client id the callback names, the ID token's issuer, audience, expiry and nonce checked (its signature is not: it comes straight from the token endpoint over TLS, which OIDC Core §3.1.3.7 allows); a callback with another `state` gets a 400 and the sign-in waits on. The Keychain holds one small JSON secret: the refresh token, the issued client id, this machine's `ext_agent_host_id` and the account's subject and email, well under the 4,096-byte line `security -i` reads (a test checks it with 2 KB JWTs). Access and ID tokens stay in memory: a process refreshes when it first needs a token, two minutes before expiry and once on a 401, one refresh at a time since each rotates the refresh token; a refreshed ID token must name the same account. If the rotated refresh token can't be saved, the process keeps it in memory and says so. Nothing saved, or a refresh token refused (400 `invalid_grant`, 401), moves the compactor to the next engine; a token endpoint that fails, a store or secret that can't be read is a reported model error, not a failover. Every endpoint, the port and the client id are configurable (`openai` in `optchat.config.ts`). `src/openai/responses.ts` streams the Responses API and reads the SSE events with Schema: text deltas, `response.completed` with usage (cached tokens become `cacheRead`, so `cold` works as for Claude), `response.failed`, `response.incomplete`, `error`, refusal deltas. `src/summarize/openai-plan.ts` is the compactor; `src/summarize/step.ts` holds what both compactors send (context pieces, step, retry text, cut, shortest try) and the size retries themselves; each engine adds only its transport, and every try with known usage gets its `usage.jsonl` line, failed ones included; a try that fails before it reports usage (HTTP 429 or 5xx, the network, the token) gets none. A failover is reported once when an engine goes down and once when a call started after that answers on it again (a call already in flight proves nothing). The same rule makes one edge silent: a call that started while an engine was down and fails on it after a newer call brought it back moves on to the next engine with no notice, and the engine stays listed as up, since that failure says nothing about the engine now; the next call started after it reports it if it is still down. Each chain's watcher (`watchChain`) numbers the calls of its own chain; the compactor also lists the engines down right now, with why, for clients that connect later. The session state carries that list as `down` (from `makeSummarize`'s `down`, given to `makeSession` as `compactorDown`, which subscribes to its changes), and each such notice publishes the state again, so a client that connects after a failover still sees that compaction fell back, and why. `optchat.config.ts` now runs Luna below level 3 and Sol from 3, each falling over to `claude-code:sonnet`, so nothing changes until the login. `dev/bakeoff.ts` replays messages from a data dir or an OptMem `LOG.txt` through each chain into its own temp data dir and reports tries per node (mean, p95: every model call logged for the node, size retries, failed calls and calls after a failover included), nodes left unbuilt at its deadline (2 hours per contender by default), calls and tokens per message, failovers, nodes over 512 bytes, user's words kept (the share of the user's sentences of four words or more that still have four words in a row verbatim in their node at levels 0, 2 and 3, plus the mean share of such runs kept), and findability (fill-in-the-blank questions from the user's sentences, answered from the view and zoom; the answerer in the box is a lexical descent with no model, and a model-backed answerer takes the same type). Its api-key contenders' records also go to `$HOME/usage.jsonl`, so the monthly budget counts them: a server that is running sees them at its next start or month, since it reads the month's spend once. All of it is tested offline against fake OAuth and Responses servers and fake compactors. Still to do: the real login, one real compactor call to confirm the route's shape, then the bake-off over ~500 real messages for Luna, Sol, Sonnet and a split, and the cutoff from its numbers.
5. **M4, MacBook as a device.** Device runner, routing, the device screen. Done when one chat edits files on both machines.
   - *Built (2026-10-05).* `device/` is the runner: one WebSocket per process (`GET /spawn`, a handshake being a GET; the spawn request is the first frame), JSON frames tagged `Spawn`/`Stdin` in and `Spawned`/`Refused`/`Line`/`Exit` out. A process lives as long as its socket: a disconnect, the daemon's SIGTERM or the end of the request kill its process group, SIGTERM then SIGKILL after `KILL_GRACE` (tested with a child that ignores SIGTERM, and through `optchat device` under SIGTERM). The runner and the local runner start `claude` through one `spawnProcess` (`src/claude/process.ts`), so exit codes, signals and stderr read the same from both. Machine auth: the runner listens on `tailscale ip -4`, refuses requests with an `Origin`, and asks `tailscale whois --json` for each caller (cached, bounded), letting in only the node whose full MagicDNS name is the server's device's; `OPTCHAT_DEVICE_TRUST=loopback` lets in local callers only, for development. `RemoteRunner` (`src/claude/remote.ts`) feeds the same `makeClaude` as the local runner. Everything up to the `Spawned` frame (no runner, a refusal, a socket dropped, no answer in 15 s) is `DeviceOffline`, so the chain can fail over, and an unreachable device is remembered for 5 s; a connection lost after that ends the turn with a `ModelError`, since the turn may have changed files by then. The server's own device keeps the local runner. Every `claude` is started with the system prompt inline as `--system-prompt`, the Mini's too (`src/claude/args.ts`), so "same bytes, same cache key" holds by construction, and the runner reads no file; for other devices the cwd goes unexpanded so `~` is the device's home, and `--mcp-config` points at `server.publicUrl` with the same secret key (E8); without `publicUrl`, turns on other devices are refused. `/api/devices` asks each `/health` with a 2 s timeout, reports online, offline or refused, and posts an `info` once per set of differing `claude` versions among online devices. launchd templates are in `deploy/`. Not done: the web UI's device screen (the `/api/devices` data is there), and a live two-machine run over a real tailnet.
6. **M5, failover.** Master chain to Sol with our own tool loop (read-only tools first), API-key overflow with a budget. Done when exhausting the Claude limit in a test switches engines without losing a message. (Since the composer pass, the switch is the user's resume, not automatic: E4.)
   - *Built (2026-10-05), not yet measured.* `src/turn/loop.ts` is our own tool loop, shared by `openai-plan` and `api-key` as the master, each on a provider (`src/providers/`: the Responses API, or an API key's Anthropic or OpenAI): the same system prompt text as `claude-code` (`instructions` on the Responses API, `system` on Anthropic), one user message of the view blocks and the new texts, the read-only tools (Read, Glob, Grep on the turn's device, through its runner's `POST /tool` or in-process; zoom and date answered from memory with docs/optchat.md §6's descriptions) as function definitions, text deltas streamed live, each text item logged as `talk` and each call as `tool` "name json" as soon as the provider says it is complete (so text after a call streams under its own log index), results as `echo` capped at `CAP` (the model sees the same capped text), thinking only by its size, one usage record per request with `failoverFrom`, a failed request's too when it says what it cost (priced on an API key, so the budget counts it). A reply cut at the output limit is said in an `info`. Mid-run messages offered to the call join after the current tool results, logged as `user` when taken; the turn ends at the first reply with no calls, and the 40th request (`TOOL_ROUNDS`) is sent with tool choice `none`; a call it makes anyway is logged with an `echo` saying it was not run. The Responses client gained function tools and an API-key bearer instead of a second client. `api-key` is Anthropic's Messages API (raw HTTP through Effect's client, like the rest; thinking blocks sent back with their signatures, effort as `output_config.effort`) or OpenAI's Responses API with a key, both as master and as compactor; keys come from Secrets (`optchat key anthropic|openai`). Anthropic's requests follow E26: a `{type: "ephemeral"}` mark at each cut of the first user message's view (or a compactor's context pieces), (the view has at most 3), plus the top-level automatic `cache_control` on every request, which marks its last block, so each request of a turn reads everything the one before sent; that is Anthropic's limit of 4 (the fake Messages API refuses a fifth, as the real one does). Every entry is 5-minute, the API's default, and there is nothing to configure (E6 is the subscription's). Prices per model ($/MTok for input, output, cache read, cache write per TTL; Anthropic's `usage.cache_creation` splits writes by TTL, and an unsplit write is priced at the dearer rate) give each record its `dollars`; a monthly budget sums this local month's api-key dollars from `usage.jsonl` once, keeps the sum in memory, and from the call that finds it spent fails every api-key call with `UsageLimit` and one `info` ("API-key budget for 2026-10 spent: $x of $y"). No `apiKey` block, no price for the model, no key, a signed-out plan: each is a `UsageLimit`, so the chain moves on and ends with a notice. `optchat.config.ts` runs `claude-code:opus` → `openai-plan:gpt-6.1-sol` → `api-key:anthropic/claude-opus-5-5`, $20 a month, with placeholder prices to verify. Tested offline: the done-criterion through the real server (a spent Claude plan on the MacBook device → openai-plan streams a reply after a Read through the device runner; the message answered once; `failoverFrom` in `usage.jsonl`; the `info` on the client), a mid-run message joining before the next request, a limit after partial output handing it on, the tools' folder boundary, and the api-key marks, prices and budget against a fake Messages API. Reasoning on the Responses API follows E26 (see "Compactor calls", openai-plan): each reasoning item comes back with its encrypted content and goes out again in every later request of the turn, with `reasoning.context: "all_turns"` and the view's breakpoints, so Sol keeps its reasoning across tool rounds and after a mid-run message; the fake Responses API issues encrypted items and refuses one it didn't issue, as `store: false` would. Still to measure with real accounts: whether the plan route accepts function tools and `tool_choice` as the public Responses API does, and our Responses cache fields (see the open question), the real Sol and Opus 5.5 model ids, real prices, cache hit rates on api-key turns, and how a real Claude Code reports a spent plan mid-turn (we match `usage limit` in the result text). Not done: write tools (Bash, Edit, Write), WebFetch and WebSearch on non-Claude engines; the budget check is not atomic across the compactor's 8 parallel jobs, so a month can overshoot by a few calls.
7. **M5.5, capability gateway.** The master gets the user's real capabilities (project repos, Cloudflare, PostHog, Gmail, …) through one code-mode gateway, preferably [Executor](https://executor.sh/), instead of one MCP server per capability. Reasons: dozens of MCP servers would put hundreds of tool schemas in every turn and change the cached prefix whenever the set changes (E6), while behind a gateway the master sees a fixed few tools (search, execute) plus our own `zoom` and `date`; a script filters big results (PostHog queries, Cloudflare listings) before the model reads them; and every engine gets the same capabilities (E4) — `claude` through `--mcp-config` with the binary unmodified, our own tool loop (M5) through the same two tools — so a change of engine changes the model, not what it can do. Memory and file tools (`zoom`, `date`, Read, Glob, Grep) stay direct tools: each step there depends on reasoning about the last result, so a script would not save rounds; code mode pays where the steps are mechanical (many tools, big structured results, fan-out). Starts with a spike: does Executor self-host on the Mini, how is its sandbox isolated, where does it keep credentials (Keychain, never the data dir). Guardrails before any production capability: per-server allowlists, read-only by default, destructive operations (deletes, deploys) behind an explicit flag, and every executed script logged next to `usage.jsonl`. Done when a turn on each engine answers a PostHog and a Cloudflare question through the gateway, and `usage.jsonl` shows requests per turn and tokens per turn against direct MCP.

- [x] **M2:** does TanStack AI's WebSocket adapter really let several clients watch one server-owned run and send mid-run messages? Not as shipped (`@tanstack/ai-client` 0.36.1): `webSocket()` opens its socket only inside `send()`, so a client that only watches never connects, and a close without durable offsets fails the subscription instead of reconnecting. `useChat`'s `sendMessage` also queues a message while a run streams (so a mid-run message would wait for the run to end instead of being steered into it) and shows it under a client id next to the server's logged copy. `useChat({ live: true })` over our own `SubscribeConnectionAdapter` got further (it connects at once, reconnects, rebuilds from each `MESSAGES_SNAPSHOT`), but its message model doesn't keep our ids: its stream processor attaches a `TOOL_CALL_START` to the assistant message in progress and renames pending messages, so a row's id drifted mid-turn (a tool row's open state reset, "show in chat" landed on the wrong row), and its window couldn't be merged with older pages without losing the stretch between them. What ships: our own link (`web/src/lib/connection.ts`) and session store over the same AG-UI events, keyed by log index; messages and aborts go straight to the socket, and the composer keeps its own unlogged messages in the Queue until the server's `ack` for their id.
