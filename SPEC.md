# optchat-du-jour build spec

Oct 5, 2026 · Piotr Monwid-Olechnowicz (hasparus)

## Purpose and sources

We build optchat-du-jour, our own OptChat: Victor Taelin's endless chat whose history is its memory, kept as a binary summary tree. It runs on the Mac Mini and serves the MacBook and the phone over Tailscale. [docs/optchat.md](docs/optchat.md), Taelin's spec kept verbatim, is the source of truth; shitty-optchat is the reference implementation we mirror module for module where it agrees with it, without copying its code. This spec refers to docs/optchat.md by section and lists only what we add or do differently, and why.

What we add on top of the reference:

- A web UI (React + shadcn) with chat, memory browser and stats, next to a terminal client.
- Several devices: the Mac Mini owns memory; turns can run on the MacBook.
- Engines matched to the plans we already pay for: Claude Max for main turns, ChatGPT Pro for the compactor; an API key is opt-in, off by default.

## Relationship to the reference implementation

docs/optchat.md is the source of truth, above the reference. Where they agree, the core matches shitty-optchat 1-1: same modules, same constants, same on-disk format, same turn mechanics. The reference follows the earlier gist; where docs/optchat.md changed something, we follow it (E22: the view's merge order, its sawtooth and `chat/view.json`, which the reference ignores) or say why not (E23, E24, E26). We write every line ourselves from its SPEC, not from its source. Its data dir and ours must be interchangeable, so its `optchat view` can read our memory and vice versa (each folds its own view).

Rules:

- Everything the reference measured (ref §14) is taken as given until our own runs disagree. Re-run its probes after any Claude Code upgrade.
- Its deviations from the earlier gist (D1–D10, ref §11) apply unless this spec overrides them. Ours are numbered E1, E2, … and listed under Deviations.
- The pure kernel is written in Bend 2 and compiled to JavaScript (E14): `id+n` addressing, the merge order (`fit`), the view's sawtooth, the rebuild from the log, `first` and the start rule (`window`, and `offers`, the scan the pump's queues are tested against). The laws under "Bend laws" are proved; what they leave open (which pair `fit` merges, and the rebuild's relation to the log) is tested against a model and the reference. It never sees text, only sizes as integers.
- Effect is the runtime for everything with I/O, time or concurrency (E13), and owns all text: rendering, cutting, logging.
- Tests follow ref §10: few, each a real failure scenario, with a fake `claude` and a fake compactor. No model calls in `bun test`: a preload (`test/preload.ts`) makes `claude` a stub that refuses to run unless a test names a fake, and points the secrets store at an empty file, so a test that forgets a fake fails instead of reaching a real model or key. The web UI's end-to-end server runs the fake `claude` with an empty secrets store too.

**Bend laws (`LAWS.bend`).** The compiler demands a proof of each on every edit:

1. The view tiles messages 0 to T with no gap and no overlap, after `fit`, `append`, the rebuild and the catch-up of a saved view (`extend`).
2. Every part `(l, i)` starts at `i · 2^l` and covers `2^l` messages; `coords` answers `(l, i)` for `id+n` exactly when `n = 2^l`, `id = i · 2^l` and `id + n ≤ T` (`coords_names`, `coords_complete`).
3. `fit` and the sawtooth merge only an adjacent sibling pair whose parent is built, and never split a part (`fit_merges`, `saw_merges`, `append_merges`); a view within its budget `fit` leaves unchanged (`fit_within`), and a view within `VIEW_HIGH` that owes no batch the sawtooth leaves unchanged (`saw_within`). Between batches the view only grows at its end: when the view after appending is within `VIEW_HIGH` and no batch is owed, `append` is the old view with the new line after its last (`append_grows`), so every turn's view is a prefix of the next one's (the cache property).
4. After `fit`, the view's size is at most its budget, or no pair can be merged (`fit_fits`). A batch ends at most `VIEW_LOW` or with no mergeable pair left, and owes the rest exactly when it ends over `VIEW_LOW` (`saw_batch`).
5. The start rule (docs/optchat.md §4 "The order"): `offers(levels, window(T, ps, n))` holds a message's node only when at most `n` view lines before it are unbuilt (`n = AHEAD − 1`: fewer than 8), and a merge only when both its halves are built (`offers_allowed`); it holds every node the rule allows (`offers_complete`). `first` is the first unbuilt view line's start, every line before it built (`first_first`): a compaction's view stops there.

Not proved, and said so: which pair `fit` merges. That it is the most due one, ties to the leftmost (docs/optchat.md §3.2), is checked by `test/kernel.test.ts` against a literal model on seeded random runs and against Taelin's rollback push (every step t = 0..20,000 with push's list length as the budget, as docs/optchat.md §3.2 reports; the first-message rule matches at only 481), not by a law: a proof needs the cross-multiplied due comparison to be transitive, i.e. Nat lemmas on multiplication (monotonicity, cancellation by a positive power of two) that the proofs don't have yet. Not proved either: the pump's queues (§7 mistake 13), which never call `offers` (a scan of the tree). `test/compaction.test.ts` holds what they start, plus what failed and waits for the next message, to `offers` after every step of seeded random runs, and times a 16,000-message backlog. Laws 2 and 5 are exact, given the input test's one `levels` flag per node, which is what makes `offers_complete`'s `Within` premise safe: `coords_names` and `offers_allowed` are soundness (alone, they would hold for a `coords` that answered "No line" to every address and an `offers` that offered nothing), and `coords_complete` and `offers_complete` the converse. `fit_merges` is soundness only (see above), and no law says the rebuild equals appending every message (see the open questions). A false variant of each sawtooth law (`append_grows` while a batch is owed, `saw_batch` ending within `VIEW_HIGH` or never owing, `saw_within` while owing, either merge law with a line added or dropped) fails the check, and so do kernels that merge at every message, never owe a batch, ignore the debt, or drop the new line. These mutations check the sawtooth, not the merge order: no law states the order, so a `pick` mutated back to the first-message rule fails only because the proofs mirror the code; the push-equivalence test is what checks the order. The laws take their inputs at their word; `test/kernel.test.ts` checks on seeded random trees that what `src/kernel.ts` hands the kernel is the tree's: each line's built flag and size, its `ups` (non-empty exactly when its parent is built, and the parent a merge makes is that parent's own line), a view that tiles `[0, T)`, the marks and the debt it was given, and one `levels` flag per node of the chat.

The parity test runs the compiled kernel against the reference, which also guards against bugs in Bend's young compiler. If the M0 spike shows the JS output can't be called cleanly from TypeScript, the kernel is written in TypeScript and the laws become property tests.

**Parity test.** A script replays a fixture log through both implementations with the same deterministic fake compactor, whose line depends on the node and its source only: the contexts part by design (theirs the bare view lines, ours the compaction view, docs/optchat.md §4). It replays twice: caught up (the compactor finishes everything after each message), and lagging (`test/parity/fixture.ts`: 1,400 messages logged in batches ahead of the compactor, its calls released one at a time between batches, about one in five failing; theirs retried after a short `retryMs`, ours when the driver, waiting, says a message is coming, `chat.retry`). The log must match byte for byte, and the tree records as a set. Caught up, the compactor calls match in order; lagging, as a multiset: the start rules part by design (theirs the earlier gist's rule 3, ours docs/optchat.md §4 "The order"), and our order is held to the proved `offers` by `test/compaction.test.ts` instead. The views part by design too (E22), so every `optchat view`, ours or theirs, of either data dir, must be a well-formed view tiling the whole log; ours prints its saved view, and on the reference's dir (no `view.json`) rebuilds one and says so. It runs in CI against a pinned reference commit. Only options the reference's `openChat` already takes are used (`summarize`, `jobs`, `retryMs`); its checkout is never changed.

## System shape

One server process on the Mac Mini owns memory; everything else is a client or a runner. Memory has a single writer, as docs/optchat.md §1 and the reference require.

- **Mac Mini, `optchat-server`** (launchd): log, tree, view, compactor pump, turn loop, priming, HTTP + WebSocket API, zoom/date MCP endpoint, and the built web UI as static files.
- **Every other machine, `optchat-device`** (launchd): spawns `claude -p` there when the server asks, streams its events back. The Mini needs none: the server spawns its own device's `claude` directly.
- **Clients:** the web UI (phone, MacBook, Mini) and the terminal REPL. Both speak the same WebSocket API.
- **Model engines:** Claude through the `claude` binary on a device; OpenAI through the Responses API with the ChatGPT plan token; an API key when one is configured (opt-in, off by default).

**The models are choices, not decisions.** The shipped chains and efforts are defaults pending the bake-off ([TODO.md](TODO.md), "The bake-off"), and `optchat.config.ts` lists the alternatives as commented-out examples (docs/optchat.md §4's Haiku at xhigh, Sonnet, an API key). Any chain entry, in the master's or the compactor's, may carry its own effort, written `"engine:model@effort"` or `{ ref: "engine:model", effort }` (the two are one entry: the `ref` text is `engine:model@effort` either way, so one model at two efforts is two engines, while an entry at its role's effort is the bare `engine:model`, the same engine), and falls back to its role's `effort` without one, as far as its model takes it ("Haiku and effort"); a ref has one effort at most, a chain that names one engine twice, in any spelling, is a configuration error (an engine is what runs: the model and the effort it runs at, so `claude-opus-4-6` and `claude-opus-4-6@high` are one in a chain at `xhigh`, which Opus 4.6 lacks), and a date after an `@` (Vertex's `claude-sonnet-4-5@20250929`) is the model id's, not an effort; `low`, `medium`, `high`, `xhigh` and `max` are the efforts, and anything else is a configuration error at startup. The media caption chain takes them too. Defaults run on subscriptions (`claude-code`, `openai-plan`); API keys are opt-in, with an `apiKey` block of prices and a monthly budget (SPEC "Usage and cost tracking"). `dev/bakeoff.ts` takes the same refs, read with the same checks, so a contender can be one model at several efforts.

## Storage, tree, view and compactor ordering

Implement docs/optchat.md §1–§4 as ref §3 does, including its "as built" decisions, except where it lags docs/optchat.md (E22), we keep the earlier gist (E23), adapt §4–§5 (E24) or differ in the cache marks (E26).

- **Records:** `main` is `{i, kind, text, size, date}` with `kind` one of `user|talk|tool|echo|note` (E23); `tree` is `{l, i, text, size}`, plus `clipped: true` after them on a node that is its source cut to fit (E33), written only when true. Our lines may add keys after these, which the reference ignores: `device`, where the turn that logged the entry ran (E7), and on an `echo` whose tool failed `error: true` (E28), written only when true, so every other line is byte for byte the reference's. A level-`l` node covers 2^l messages from `i * 2^l`.
- **Writes:** one write plus `fsync` per line, files split by local day, ids global. On load, skip and report damaged lines and add a missing final newline. Only the lock holder repairs.
- **Lock:** a unix socket per stream for the process lifetime; a refused connection means stale and taken over. Keep paths under ~107 characters.
- **Free nodes:** level 0 is `kind + ": " + text` if it fits in `NODE`; higher levels are `childA + "\n" + childB` if that fits. Written to `tree` like any node; no model call.
- **Pump** (docs/optchat.md §4 "The order", `src/compactor.ts`): a message's node starts once fewer than `AHEAD` view lines before it are unbuilt, a merge once both halves are built; at most `JOBS` at once. Ready nodes wait in queues kept as messages arrive and nodes are built (the unbuilt messages in order, whose first `AHEAD` may start; the ready merges per level), never found by a scan; the one scan is at startup. Messages go first, then merges, lowest level first, oldest first (the spec leaves the order open). A failed call waits, unreported after its first failure, until the next message is logged or reaches the session (`chat.retry`), and, only while a turn waits for summaries, every `WAIT_RETRY` (E24). A logged entry tries it again only once it has rested `WAIT_RETRY` (E33): a turn logs its entries back to back, and each would otherwise ask a vendor that is down again at once; a message reaching the session and the waiting turn's retry don't wait. And while any call has failed, one fiber of the pump tries each again as it has rested, so a node that failed near a turn's end isn't left until the next message, unbuilt, with the idle view unprimed. Each failure in a row doubles the node's rest, from `WAIT_RETRY` up to `REST_MOST` (5 min), so a long outage or a spent plan settles to one call per node every few minutes; a success starts it over. A call the model refused, or whose reply ended as it meant to with an empty line (no line before it), fails as `NoLine` and counts against the node; at `REFUSALS` the node is built without another call from its source, clipped (E33), and that is reported once. A limit, an outage, a reply cut short by its token limit or the context window, or a crash never counts: those are only tried again. The job's context is snapshotted when it starts.
- **Compaction view** (docs/optchat.md §4 "Its view"): the view merged further, `COMPACTION_HIGH` down to `COMPACTION_LOW`. When the view merges, it is the view batched to `COMPACTION_LOW`; otherwise it gets the view's new line and runs its own sawtooth (the kernel's `append` and `saw` at its marks). A compaction sees its lines that end by the node (a message's: the lines before it; a merge's: up to its last message), stopping at the first unbuilt line (`first`), as `id+n|text`.
- **View:** which pairs merge: the most due built pair, `due = (T − last) / 2^l` measured from the pair's last message, ties to the oldest (docs/optchat.md §3.2; the kernel compares `(1 + T − e₁)·2^l₂` against `(1 + T − e₂)·2^l₁`, `e` the pair's end). When: a message appends its line and nothing else changes; once the view passes `VIEW_HIGH`, one batch merges down to `VIEW_LOW`. A batch that parents not yet built stop over `VIEW_LOW` is owed (`folding`) and goes on at each later message until it reaches `VIEW_LOW`; a node being built never changes the view's lines. Never split. Size is the sum of the lines' texts, not of the rendered `id+n|` lines and newlines (2–3% under the rendered bytes, as the reference); an unbuilt line counts `NODE`, the most its summary may take, so lines built after the last message never take a view that owes no batch past `VIEW_HIGH` (a summary a few bytes over `NODE` aside), and a compactor outage shows as a batch owed. `fit(T, budget)` and the sawtooth take their marks as parameters, so a second view can run its own.
- **`view.json`:** in `chat/` beside `main/` and `tree/`, where docs/optchat.md §1 puts it, but `{"folding":bool,"view":[[l,i],…],"compaction":{"folding":bool,"view":[…]}}` rather than the bare `[l, i]` pairs: the debt must survive a restart (E22), and so must the compaction view, whose batches depend on when it passed its high mark and what was built then, so it can't be derived from the view. One file, one atomic write: the two never disagree. Under the stream's lock, written by its holder only. Rewritten whole after each message's log line is synced (temp file, fsync, rename, fsync of `chat/`), so the log is never behind it. A save that fails is reported and the writer carries on: the message is logged, the next save rewrites the whole file, and a file left behind is caught up at load. Loaded at start, never rebuilt (§3.2, §7 mistake 3); every load reads it before the logs, so a reader racing the writer finds it at most behind them. Its lines must tile `[0, T′)` with `T′ ≤ T`, every merged line built; `T′ < T` appends the missing messages (`extend`: the first as `append`, the rest with the rebuild's skips, so 3,000 behind takes about as long as a rebuild); missing, unreadable, not a file or illegal, the view is rebuilt from the log once, reported, and saved, after the writer moves a non-file aside (`view.json.broken-<ms>`); a reader without the lock rebuilds for itself and writes nothing. A compaction view that is missing (an older file), illegal or behind (the view had to catch up) is batched again from the view, once, which costs only compactions' cache entries. The reference ignores the file.
- **Render:** `<chat>\n` + `id+n|text` lines with newlines turned into spaces + `\n</chat>`. Unbuilt lines show `(not summarized yet: zoom it)`.
- **`settle(signal)`:** resolves when every view line is built. A turn waits on it before rendering (docs/optchat.md §6).

**Streams (E3).** Each writer gets `streams/<device>/` with its own `chat/`, lock and pump. In v1 only `mini` exists. In offline mode (M6) each stream's owner compacts only its own tree, and every view appends the other streams' folded views read-only as `<chat who="macbook">` blocks, as Intrepidus does.

## Engines

Every model call goes through one of three engines. The compactor and the captions choose per call from a failover chain; a master turn runs on the engine of its chain its messages name, the chain's first when they name none (E4). Because each turn starts fresh from the view, any engine can take any turn; memory doesn't care who wrote what.

```ts
interface TurnEngine {
  run(input: { view: string; texts: string[]; device: string; signal: AbortSignal },
      out: TurnEvents): Promise<TurnResult>;   // TurnEvents: talk, tool, echo, replay, usage
  steer(text: string): void;                    // mid-run message
  prime?(view: string): Promise<void>;
}
interface CompactEngine {
  summarize(job: Job): Promise<string>;        // job: context lines, step block, level
}
```

(With Effect these become services returning `Effect`s; interruption replaces `signal`. As built, `steer` is gone too: the session offers mid-run messages on the call's input and the engine reports each one it took, `src/turn/engine.ts`.)

| Engine | Auth | Used for | Notes |
| --- | --- | --- | --- |
| `claude-code` | My Claude Max login, in the unmodified `claude` binary on each device | Main turns (Opus, high effort); spare compactor capacity (Haiku, xhigh) | Exactly the reference's mechanics (ref §4–§7). Never read or reuse its OAuth token elsewhere |
| `openai-plan` | Sign in with ChatGPT, "Use your ChatGPT plan" scope, ChatGPT Pro | Compactor (Luna, Sol); master fallback (Sol) | OAuth 2.0 + PKCE; the first sign-in sends `client_id=dynamic_agent_client` and gets this install's own client id back, which is saved and used from then on; Responses API with `stream: true`, `store: false`, cached as E26 says (see "Compactor calls") |
| `api-key` | Anthropic and OpenAI keys with a monthly budget | Opt-in, off by default: needs an `apiKey` block and a ref in a chain | docs/optchat.md §3.3's cache layout: a mark on the view's last whole block plus the request end, and on Anthropic one on the system prompt (E26); 5-minute entries only, nothing to configure |

**Refs.** A chain's entries (`engine:model[@effort]`; `api-key:<provider>/<model>[@effort]`) are decoded once, with the settings, into typed refs (`src/config.ts`), so a ref no engine takes is a configuration error at startup and nothing after that parses one again. `src/engines/registry.ts` is the one place that turns a ref into a turn or compactor engine, and where the effort an entry runs at (`runEffort`, see "Haiku and effort") is handed to the engine: `claude-code`'s `--effort`, the Responses API's `reasoning.effort` (`openai-plan`, and `api-key` on OpenAI), Anthropic's `output_config.effort` (`api-key`), or none of them when it runs at none. The picker's label shows an entry's own effort ("Claude Haiku (Claude Code, xhigh)"), and for an entry without one, the effort it runs at when that is not the master's ("Claude Opus 4.5 (Claude Code, high)", "Claude Haiku 4.5 (Claude Code, no effort)"). The session and the web client read a ref spelled with the master's own effort as the bare one, so a pick kept from before the master's effort changed still finds its engine. The ChatGPT plan's client and the API keys' clients are built on first use, so a server whose chains name neither engine never builds them.

**Failover** (the compactor's and the captions' chains; the master doesn't fail over, see below). Move to the next engine in the chain on a usage or rate limit, on `429 subscription_sharing_usage_limit_exceeded` from OpenAI (also when it ends a stream as `response.failed`), when `openai-plan` is signed out or not eligible (`403 subscription_sharing_user_not_eligible`, or a 401 that one token refresh doesn't cure), when the device is offline, or when Anthropic is overloaded (`529 overloaded_error`: Claude Code's error result or its synthetic message says `overloaded`, an api-key call gets the 529). An overload is transient, and a retry a few seconds later might go through on the same plan, but E4's point is to keep chatting: the next engine answers now, where a failed call would leave the node or caption to wait. On our own HTTP engines (`api-key`, `openai-plan`) the request is first sent again a few times on the same engine (E35): an overload, a rate limit with a short `retry-after`, a server error or a dropped connection reaches the chain only once those tries are spent; a plan's cap, a key out of credit and a `retry-after` past `HTTP_RETRY_LONGEST` reach it at once. `claude-code` has Claude Code's own retries. For the master an overload, like any usage limit, stops the turn until it is resumed, and resuming on the same engine is the retry. Never on a refusal or a model error: those are reported, as in ref §5.2. Each failover is logged to `usage.jsonl` and shown in the UI.

**Mid-run messages on `openai-plan`.** The reference relies on Claude Code delivering stdin messages between tool calls. On the Responses API we run our own tool loop, so a steered message is appended after the current tool results, before the next request.

**Tools on non-Claude engines.** Claude Code brings Bash, Read, Edit, Write, Glob, Grep, WebFetch, WebSearch and TodoWrite (the default `master.tools`; TodoWrite is its todo list, the web UI's Plan). A Sol turn gets the same set but TodoWrite, implemented by the device runner, plus zoom and date (and spawn, tell and the artifact tools, as `/mcp` has them). Its first version (M5) ships read-only tools only, so a fallback turn can answer but not change files.

**The master picks no engine by itself (E4).** Each message names the engine of the master's chain it is for (`forwardedProps.engine`, a ref, decoded by the `/ws` schema): the composer's model picker or the REPL's `/model` when it was sent. One that names none (an older client, a piped REPL) or a ref the chain lacks (said in an `info`) is for the chain's first. The chain is the list the pickers offer, labelled for people ("Claude Opus (Claude Code)", "GPT-6.1 Sol (ChatGPT plan)", `engineLabel` in `src/wire.ts`). The picker is client state only (the web app keeps it per browser in `localStorage`, the REPL per process): switching sends nothing. Why no automatic failover: the plans are paid separately, and which one pays is the user's call; a turn that quietly moved to the API key or the other plan spends what the user meant to keep. Switching engines costs a cold cache: each plan caches on its own side. Priming and the warm process (E18) follow the engine of the most recent turn, the chain's first before any (`src/master.ts`); one marked down is not primed.

**A turn stopped by a usage limit or an offline device** (or an overload) waits for a resume. Refusals and model errors still end the turn as below.

- **The stop.** What the turn logged stays, once; text it streamed and never logged is dropped; what its call never took is held again. No call accepts mid-run messages while it waits: one sent meanwhile is held (it can be taken back; a cancel logs it unanswered). Then, in order: the state says phase `needs-model` with `stopped: {ref, label, why}`; the run ends with the reason (`RUN_ERROR`); the data dir is committed. No `info`: clients show the stop once, from the state (the web app's alert, the REPL's list), never as a chat error.
- **The resume** (`{"type":"resume","engine"}`: the alert's "Try X again" or "Continue with Y", the REPL's `/resume`) is the one model frame a client sends, only in `needs-model` and only while connected. The composer's picker never resumes. One with no turn stopped, a second one for the same stop, or one on a ref the chain lacks gets an `info`.
- **What goes on.** The held messages for the stopped engine, up to the first for another engine or device, go to the engine resumed on and join its call (`handOver`, `steerIn`). The rest keep their engines: with `[m2(B), m3(A)]` held after a stop on A, a resume on B joins m2 (B's already) to the call, and m3 keeps A for a turn of its own, which may stop again. The resumed run has its own run id (`<first>+<n>`); an `info` ("Claude Opus (Claude Code) stopped (usage limit: …); GPT-6.1 Sol (ChatGPT plan) carries on from the 2 logged entries", or "tried again") is the record. The engine gets the same view and texts, what was logged so far as `earlier` (under a note that another engine, or this one earlier, began the turn), the pictures of mid-run messages taken before, and the untaken messages on `mid` (E16). Its usage record's `failoverFrom` names the engine that stopped.
- **Down marks.** An engine that hit a usage limit shows as unavailable in the pickers, with why, until it answers or `MASTER_DOWN_FOR` passes; the stopped one can always be tried again. A limit is learnt only from a failed call: a signed-out engine shows as available until a turn tries it.

## Turn and priming

The `claude-code` turn is ref §4–§6 unchanged, except for the cache TTL (E6), where the process runs (E7), that it never waits for priming (E17), and that its process may have been started ahead (E18).

1. Wait for `settle()`; on cancel, log the queued texts as unanswered `user` messages.
2. Render the view **before** logging the new messages.
3. Stop any priming still in flight, without waiting for it; never prime first (E17).
4. Log each queued text as `user`, then spawn the master on the chosen device: the base flags of ref §4 plus `--mcp-config` and `--replay-user-messages`. On the Mini this is usually the warm process started for exactly this spawn (E18).
5. Send one user message: the view in blocks of `BLOCK` lines (docs/optchat.md §3.3), **no cache marks** (Claude Code's own fill the 4 slots, ref D2), then the texts joined by a blank line. Claude Code's mark at the request's end finds priming's within the 20-block lookback, unless about 18 or more pictures sit between them.
6. Map stream events to the log as in ref §5.3: text → `talk`, tool_use → `tool`, tool_result → `echo` (capped at `CAP`), later replays → `user`. Never log thinking: never in the log; kept in a side file (Reasoning, E29). Nor an assistant message of model `<synthetic>`: that is Claude Code's own, how it reports an API error (`Claude AI usage limit reached|…`, `API Error: 529 …`) just before its error result, not the model's reply. Its text joins the result's in the failure, so a limit it names fails over (E4) even when the result line doesn't say so, and it never reaches the next engine's opening message.
7. Kill the process at the first `result`; requeue mid-run messages that were never replayed. Commit the data dir. The session reports `idle` only once the commit is done, and a message that arrives while the loop winds down starts it again.

As built, where we differ from ref §5.2:

- A refusal or an `is_error` result ends the turn like a crash: mid-run messages the call never took are logged as unanswered `user` messages, where the reference requeues them after any `result`. A refused or failed call says nothing about the next one, and the user sees the messages and the error together. A usage limit or an offline device is not this: the turn waits for a resume (Engines, E4).
- A cancel before the run starts (while waiting for summaries) logs the queued texts unanswered, each after its captions (at most `media.captionWait`), since a marker is never logged without that wait. There is no wait for priming to cancel (E17).
- A blank message is ignored: it starts no turn and logs no empty `user` entry.
- Every message waits in one inbox (`src/session.ts`) until it is logged, with the id its client sent it with, and has one owner at any moment: held for the next turn, picked by the turn that is logging it, or offered to the running call. A call reads what it is offered from its own queue and reports each message it took (claude-code: its replay; our tool loop: when it joins the next request), and the session logs it then and acks that client id; what the call never took is held again when it ends, on the call's device unless it was sent for another. The inbox holds the offered messages first, then the held ones: nothing is offered once anything is held, so the log keeps the order they were sent in. The engine a stopped turn is resumed on is offered the untaken ones first, and is given what the turn logged so far (`earlier`) read from the log. Acks never match by text, so two clients sending the same text each get their own entry. The session state lists the whole inbox as `pending` (`{clientId, text, engine, queued, media?}`, in the order sent, held, picked and offered alike, while waiting for summaries or between turns too; `queued` is true for a held one, `media` its attachments as stored), so a client that reconnects can tell a message the server holds from one the dead socket lost, by its client id. Writing a message to the log and taking it out of the inbox is one uninterruptible step, so a cancel never logs it twice.
- A turn runs on the engine of the first held message. It takes the held messages from there up to the first one for another engine, or for another device than the first of them that names one, together; that one waits for the turn after, which runs there, with everything sent after it. The turn runs on that device (the one a message was sent for, by `/on` or the composer's picker, or for a message a call never took, that call's device), else on the default device: never on one named only past the cut. The device and the messages are read together, after the wait for summaries, so a message sent during that wait for another device gets a turn of its own. A message sent for another device or engine than the running turn's therefore is not offered to its call; it waits, and so does every message sent after it, also one for the running device and engine, so the log keeps the order they were sent in.
- **Follow-ups: steer or queue.** What a message sent while a turn runs does is a session setting, `followUp`, shared by every client (T3 Code's "Follow-up behavior"; `master.followUp` in the config until a client chooses): `steer` (the default) offers it to the running call, `queue` holds it for the next turn. A message may ask for the other (`forwardedProps.followUp`: the composer's second button or Mod+Enter). A queued message is held, so the inbox keeps its order: a message that steers takes the held ones before it into the call (`steerIn`, `src/inbox.ts`), never past the first held one for another device or engine. Messages sent while the turn waits for summaries join its batch; ones sent while it waits for captions, logs its batch or waits for a resume steer or wait once a call runs.
- **Take-back.** A held message (queued, between turns, while summaries are awaited, or while a stopped turn waits for a resume) can be taken back by its client id, by any client: one user, one shared queue, so the phone can take back what the laptop queued. It it leaves the inbox and every client is told (`taken-back`, with its text and attachments, so the client that asked puts it back into its composer); it is never logged. A turn picks its batch, and so takes those messages beyond reach, in the same synchronous step that reads the inbox, before it waits for their captions; a take-back that comes later is refused ("too late: the model has it") and the message is logged and answered once. An offered message can't be taken back: the call may already have read it. A turn whose whole batch was taken back while it waited for summaries doesn't run.
- Our tool loop leaves no `tool` entry without its `echo`: a call whose request failed after it streamed, or whose turn was cancelled, is answered with `not run: <why>`, as a call of the last allowed request is. If the log refuses mid-stream, the request is read to its end anyway (it is paid for), its usage is recorded, and then the turn fails with the refusal, reported once.
- Known: a cancel that comes while the loop winds down (the commit, the check for a newer message) does not stop a restart that a message sent meanwhile causes; the new turn runs and can be cancelled in its turn.
- After the loop stops on an error (the log refuses, a defect), the messages it stopped on wait for a newer one, so a defect can't restart it forever; a message that comes in while the loop winds down is newer and starts it again.

The system prompt is `prompts/system.txt` + `instructions.md`, built once at startup and sent inline as `--system-prompt` on every call and device (no file), byte-identical across them and across turns and compactions: no dates, cwd or git status (docs/optchat.md §5, §7 mistakes 6 and 10). The text is docs/optchat.md §5's, adapted (E24).

**Priming.** As ref §6: a call with the master's exact flags plus `DISABLE_PROMPT_CACHING=1`, carrying the same view blocks with our own marks (`ttl` per E6) on the last whole block and on the view's end, none on its `ok`, killed at `message_start`. The turn right after reads the whole view; the next priming, the view grown at its end between batches, finds the whole-block entry and writes only the lines after it. It runs only while the session is idle: in the background 1 s after the view settles, and when a web client connects, since a message usually follows. That idle priming is what makes turns warm. A turn never waits for it (E17), where ref §6 has the turn await it (docs/optchat.md has no priming and sends no keep-alive pings, §3.3):

- The same view was primed within `PRIME_MAX_AGE`: the turn reads it from the cache.
- A priming is in flight: the turn starts at once and the priming is stopped (its fiber interrupted, its `claude` killed; it logs no usage and reports no failure). Its request would race the turn's own, which writes the same prefix anyway, so letting it finish would write the view twice; killed before `message_start`, and often before its request leaves `claude`, it costs less or nothing (whether a request killed after it was sent counts against the plan is still open, see M1 below). The next idle priming writes the marks for the next view.
- Nothing was primed: the turn just runs, and its own request writes the cache, with Claude Code's mark at its end rather than ours on the view; the idle priming after the turn writes those for the next view.

Measured on claude 2.1.289 with Sonnet and a small view: a turn sent while its view was being primed showed "priming" for 2.6 s (a fresh `claude -p`: ~1.3 s to boot, ~1.2 s to `message_start`) before its own ~2.0 s to the first text. Waiting can't shorten the time to the first token; it only spares one cache write, which on the plan is quota, not latency. So the session has no "priming" phase any more: a turn is `waiting` (for summaries) or `running`.

**Warm processes (E18).** Most of a turn's first second is `claude` booting: spawned and sent a message at once, it reaches `system/init` in ~1.3 s; started ahead and idle on stdin, in ~0.1 s. So the Mini's Runner (`src/claude/warm.ts`) keeps one process started ahead for each of the next two spawns, the master's turn and its priming (which differ only by `DISABLE_PROMPT_CACHING=1`). The engine names them when the session starts and whenever it goes idle. A spawn byte-identical in args, env and cwd gets the warm process and a replacement starts at once in the background; any other spawn starts fresh. The rules:

- At most one process per spawn, and only for the two spawns named last. The session names those of the engine of the most recent turn (the chain's first before any, E4), on the default device, and only that engine warms again after a transport move; a failover link's turn, a turn on another device and one in another folder start fresh. When the two spawns change (that engine's model, the device's MCP transport), the stale processes close.
- One that dies while idle is noticed (its output closes), never handed out, and replaced after `WARM_RETRY`, at most `WARM_TRIES` times in a row, so a broken `claude` doesn't restart forever; one that fails to start counts the same. A spawn that starts it fresh again gives it `WARM_TRIES` more.
- Each spawn has a keeper fiber that starts its process, holds it in a one-process slot and waits until it is taken, dies or grows old. A caller takes it out of the slot and ties it to its own scope in one uninterruptible step, so an interrupted caller can't leave it running.
- One older than `WARM_MAX_AGE` is replaced, so no turn runs on the login, settings and feature flags a process read hours ago. Claude Code may also update itself between a process's start and its use; that turn runs on the version it started with, which is accepted (a version change costs one cache rewrite anyway, ref §16.8).
- Every warm process belongs to a scope under the server's: shutting down kills them all, like any running turn.
- Other devices (RemoteRunner), the compactor (8 jobs at once, not worth it) and the API engines spawn on demand.

Each idle `claude -p` holds about 200 MB, so the Mini keeps ~400 MB for this. It also opens its MCP connection to `/mcp` at boot, so a turn doesn't wait for that either. Measured with `dev/latency.ts` (same machine, 3 turns each, 8 s idle between them): the median time from send to the first assistant text went from 1,990 ms to 1,160 ms, and to `RUN_FINISHED` from 3,125 ms to 2,218 ms.

**Cache TTL (E6).** The reference forces 5-minute entries (`CLAUDE_CODE_PROMPT_CACHE_TTL=5m`) to follow the earlier gist. docs/optchat.md §3.3 now leaves Claude Code subscriptions their own 1-hour lifetime. On the Claude subscription (`claude-code` turns, compactor calls and priming), and only there, we keep Claude Code's default 1-hour marks instead, and priming writes `ttl: "1h"` marks. Every mark in a request then has the same TTL, which avoids Anthropic's ordering error (1-hour entries must precede 5-minute ones). Reason: on the plan there's no per-token bill, and phone chats with gaps over 5 minutes would otherwise rewrite the whole view on almost every turn. The variable is set per spawned process; my normal Claude Code settings stay untouched. An API key is billed per token, so its requests keep docs/optchat.md §3.3's 5-minute entries with nothing to configure: the old `cache.apiKeyTtls` is gone, and a config that still has it loads with the key ignored, as the schema drops any unknown key.

## Compactor calls

docs/optchat.md §4 on every engine, adapted where E24 says; only the transport changes (E5). The level of the node picks the engine chain.

**Input, all engines** (`src/summarize/step.ts`). What a turn sends before its view, byte for byte: the one system prompt and the turn's tools, never called (§7 mistake 6). Then the compaction view's lines up to the node as `<chat>` + `id+n|text` lines + `</chat>`, in blocks of `BLOCK` lines like a turn's view, then the task, verbatim from §4: "Compaction: compress message {id} …" with the message whole, or "Compaction: merge lines {a} and {b} …" with the two lines as the view shows them (`id+n|text`), each under a ruler of 512 dashes.

**Size retries.** In the same conversation, §4's "Too long: your line is N bytes, over the 512-byte limit. …" + the line cut at 512 bytes + `| ← LIMIT`. Up to `TRIES`; keep the shortest try.

**In-flight prefix** (§3.3, `src/engines/inflight.ts`). A call (on claude-code, before its process starts) whose marked prefix (engine, model, system prompt, tools and the context up to its last mark, as the marks helpers place it) another call is writing waits until that call's first response event; one with nothing marked before its end never waits; a writer that ends before its response starts hands over to the next. Turns don't need it: priming is stopped when a turn starts (E17), and no other call shares a turn's view.

Per engine:

- **`claude-code`:** a turn's flags on the server's own device (`baseArgs` with the same `--system-prompt` and `--tools`, `--mcp-config` with zoom and date, `--strict-mcp-config`, cwd) but for the model, its effort and `--permission-mode default`, and without `--replay-user-messages`, which shapes claude's output, not the request; no `--safe-mode`, which drops the MCP servers. With `-p` and `--setting-sources ""` nothing is allowed ahead, so `default` refuses Bash, the writing tools and the MCP ones; Read, Glob and Grep need no permission, so a try is killed at the first `content_block_start` of a `tool_use`, before claude can run it. `DISABLE_PROMPT_CACHING=1` with our 2 marks (the last whole context block and the task), TTL as E6. Its `Spawn` is never pooled (`pooled: false`): no warm process is started for it or handed to it (E18).
- **`openai-plan`:** Responses API with the tool loop's `instructions` and function tools (the default device's), `tool_choice: "none"`; one request per try, the full input re-sent each time (`store: false`). Cached as E26 has it, on every request of every engine that speaks it (this compactor, the api-key OpenAI one, and our tool loop as master): `prompt_cache_breakpoint: {mode: "explicit"}` on the last whole context (or view) block, the same in every round and size retry of one call (a later call's moves on, and finds this one by the lookback); the request end cached implicitly (`prompt_cache_options` left at its default); `include: ["reasoning.encrypted_content"]`, and every reasoning item a reply holds sent back verbatim in the next request (the next tool round, or the next size retry), ahead of what followed it; `reasoning.context: "all_turns"`, so a mid-run message doesn't drop the earlier reasoning and miss the cache. A model that answers 400 naming `prompt_cache_breakpoint` (the reference measured the Codex route doing that for `gpt-6.1-sol`) gets the same request again without it, and none from then on, which is reported once; it then caches only what OpenAI caches implicitly. The route rejects `system` messages, so the system prompt goes into `instructions`, as OpenAI's docs for the route say. Each try is one user message of input-text parts (the context pieces, then the task), and a retry appends the previous reply's output (its reasoning items and its text as an `assistant` message) and the retry text as a new user message.
- **`api-key`:** the api-key turns' `system` and tools, tool choice `none`; on Anthropic the system prompt carries a mark, as a turn's does (E26); then the context pieces with a 5-minute mark on the last whole one, the task after them, and the top-level automatic `cache_control` on every try, so a size retry reads the whole try before it; OpenAI is the same as `openai-plan`.

**The model.** docs/optchat.md §4 uses Claude Haiku at xhigh effort (`claude-code:haiku@xhigh`, or `api-key:anthropic/claude-haiku-5-5@xhigh`), and the shipped chains now match it on the Claude-plan fallback: the ChatGPT plan's model first (Luna below level 3, Sol from it), falling over to `claude-code:haiku@xhigh`. The per-level chains stay configurable (E5), Sonnet is a commented alternative in `optchat.config.ts`, and which is better waits for the bake-off. A fallback call spends the turns' Claude Max quota, though little of it on Haiku, and only a call on the turns' own model at their effort reads their cache entry, which Haiku's isn't (the in-flight wait keys on both too).

**Haiku and effort.** Which efforts a Claude model takes is known per model (`claudeEfforts`, `src/config.ts`), on `claude-code` and on `api-key` Anthropic refs; OpenAI's refs are given what they are configured with. An entry's own effort (`@effort` or `{ effort }`) that its model can't take is refused when the configuration loads, with the ref as written. Without one, the entry runs at its role's effort if its model takes it, else at the highest effort its model takes below that, else at none (`runEffort`): a role's effort is a default for the chain, not a demand on each model, so a model that takes no effort can stand in any chain and is sent no `--effort` or `output_config.effort`. Findings, as of Claude Code 2.1.295 and the claude-api skill (Oct 2026): the `haiku` alias is Haiku 5.5, which takes `low` to `max` (default `medium`), `--effort xhigh` included; `claude-haiku-4-5` takes no effort (Claude Code's model catalog lists no effort capability for it and leaves the setting out of the request; the Messages API refuses `output_config.effort` for it), and so do Claude 3, Opus 4.0 and 4.1, and Sonnet 4.0 and 4.5; Opus 4.6 and Sonnet 4.6 take no `xhigh` (a role at `xhigh` runs them at `high`), and Opus 4.5 nothing above `high`. A model is known by its family in any spelling: any case, a dated snapshot (`claude-opus-4-20250514`, Vertex's `@20250929`), a `[1m]` variant, a Bedrock id or inference profile (`us.anthropic.claude-haiku-4-5-20251001-v1:0`). Over an API key the Haiku that takes xhigh is `api-key:anthropic/claude-haiku-5-5`; a CLI older than the one that knows Haiku 5.5 resolves `haiku` to 4.5 and silently drops the effort, which no check here can see.

## zoom and date over MCP

The server exposes `zoom` and `date` as an MCP server at `/mcp` on the tailnet, so a `claude -p` on any device reaches the same memory (E8, replacing the reference's stdio server, D8).

- **Transport:** a WebSocket by default, one JSON-RPC 2.0 message per text frame each way (`GET /mcp` that upgrades); also one message per `POST /mcp`. Claude Code documents only `stdio`, `sse` and `http` for `--mcp-config`, but its config schema also takes `{"type": "ws", "url", "headers"?}`, and it connects with subprotocol `mcp` and no `Origin` (probed on 2.1.289: connected, and a real turn called `zoom` over it). A warm process (E18) opens the socket at boot and keeps it, so a turn's tool calls go over a connection already open. Because the type is undocumented, each device falls back by itself, and while on ws watches every `claude` there (priming usually comes first) for one of these: its `system/init` lists `optchat` as `failed`, or leaves it out (2.1.289 skips an entry whose type it doesn't know, with a warning on stderr only when that is a terminal); or it ends before any `system/init` because its config was rejected (Claude Code checks `--mcp-config` against its schema as it starts and exits with `Error: Invalid MCP configuration:` on stderr; 2.1.42 does that for any entry its schema refuses); or it ends before `system/init` twice in a row for any reason. `pending` and `needs-auth` say nothing about the type and change nothing. That device's calls then use the `http` form, the user is told once (in words that allow for the other cause of `failed`, a server it couldn't reach), and its warm processes (E18) are started again with the new config by the engine the warm processes follow (another link's move leaves them to the session's next warm, when it goes idle). A rejected config counts only when the error names `mcpServers.optchat`. `server.mcpTransport: "http"` turns ws off. Which transport is used changes nothing the model is sent, so not the cache either.

- **Behaviour:** exactly ref §9 and docs/optchat.md §6, with its tool descriptions verbatim. `zoom(id, n)` validates integers, `n` a power of 2, `id % n == 0`, `id + n ≤ T`, the node built; otherwise `No line id+n.` `zoom(id, 1)` returns `id+0|kind: text` in full and works for any existing message; on a user message with attachments it also returns their pictures as MCP `image` content (E20, see Media). `date(id)` returns local time as `2026-10-04 14:03`, or `No message N.`
- **Read-only:** answers from the server's in-memory tree; never takes the lock.
- **Cache stability:** the `--mcp-config` JSON is the same for a device's priming and real turns. The server name stays `optchat`, so the tool names (`mcp__optchat__zoom`, `mcp__optchat__date`) and the cached tool list are the same on every device; only the URL differs, and the URL isn't sent to the model.
- **Auth:** a `claude` on another device calls `/mcp` at `server.publicUrl`, that is through `tailscale serve`, which hides the caller's address and adds its owner's login. So WhoIs plays no part: the guard is the secret key in the URL (made at startup, sent only inside `--mcp-config`) plus the `allowedLogins` check every route has. Over either transport: the WebSocket's upgrade request passes the same Host, Origin and login checks as any request (`server/auth.ts`) and needs the same key. A `claude` on the Mini calls the loopback URL with the same key. Without `server.publicUrl` the server refuses turns on other devices rather than hand them a loopback URL and its key.
- **Artifacts (M8):** the same server has `publish_artifact`, `edit_artifact` and `read_artifact` (see Artifacts); the subagents' key may only read.
- **Subagents (M7a):** the same server also has `spawn(name, task, model?)` and `tell(name, text)`, and `zoom`'s `id` may be a subagent's name (`zoom("Name")`, `zoom("Name", n)` from its entry n), with the tool list changed once for them (`id` is `["integer", "string"]` and only `id` is required). A subagent's claude reaches `/mcp` with a key of its own, on which spawn and tell are refused; zoom and date answer it as the master's. See Subagents.
- **Offline mode (M6):** gains `who`, plus `grep(regex, who)`, as in Intrepidus.

## Multi-machine

One chat, one memory, two pairs of hands: the Mini keeps memory and the turn loop, and runs each turn's `claude -p` on whichever machine has the files (E7). The MacBook needs only `claude` logged in and the device runner.

**Device runner (`device/`).** A small Bun daemon, launchd-managed, listening on the tailnet only.

- `GET /spawn`, a WebSocket whose first frame carries the args, env and cwd; then stdin goes in and the stream-json events come out, and a last frame says how `claude` exited (`src/claude/wire.ts`). It refuses a cwd outside the configured folders, after resolving symlinks and `..`, and any env but `CLAUDE_CODE_PROMPT_CACHE_TTL` and `DISABLE_PROMPT_CACHING`, the two a turn and its priming set; and `claude` never inherits a provider key or cloud setting from the runner's own environment (E34). It only ever runs the `claude` binary, never a shell, but the caller chooses its arguments: these checks keep turns alike across devices and are not a sandbox. The boundary is who may call: only the server's device (`OPTCHAT_SERVER_DEVICE`, else `defaultDevice`), by Tailscale WhoIs.
- Kills children on disconnect, on SIGTERM and after `KILL_GRACE`, mirroring the reference's child registry (ref §5.2). Each `claude` runs in its own process group, so the kill reaches the commands it started. A daemon killed with SIGKILL (launchd stops it with SIGTERM) leaves its running children behind, for the same reason; not prevented.
- Listens on the machine's `tailscale ip -4` address only. MagicDNS also answers AAAA, so the server resolves a device's name to IPv4 before connecting.
- Writes nothing of its own; the master's tools change files on that machine, nothing else.
- `POST /tool` runs one read-only tool (Read, Glob, Grep) for a turn on an engine with its own tool loop (M5): a `ToolCall` in, a `ToolReply` out, let in on the same terms as `/spawn` (no `Origin`, a trusted node). Every path is resolved (`~`, `..`, symlinks) and must land in the folders; Glob patterns may not climb out; output is capped at 100k characters and each call at 30 s. Grep's pattern is the model's and a JavaScript regex can backtrack without end, so the search itself runs in a Worker (`src/tools/grep-worker.ts`) that is terminated when the call times out or is interrupted; the server's event loop is never the one blocked. No shell and no write. The server's own device runs the same code (`src/tools/files.ts`) in-process.
- `GET /health` returns the `claude` version, so the server can warn when devices differ (a version change invalidates the cache once, ref §16.8). `/api/devices` shows each device as online, offline, or refused (it answered 403: its callers or the server's node name are misconfigured).

**Routing.** Each turn picks a device: an explicit picker in the UI, a `/on macbook` prefix, or the default device. The choice is stored as an extra `device` field on that turn's log entries, which readers ignore, as pi-optchat does with its `origin` field. The user's text is never changed; the tool calls' paths already show the compactor where work happened.

**Device offline.** The turn fails fast with a clear notice in the UI and in the log; the failover chain may then run it on another engine with read-only tools. Never queue silently. The server remembers an unreachable device for 5 s, so a priming and the turn right after it wait for it once and report it once.

**Offline mode (M6).** If the Mini is unreachable, the MacBook runs a local server on `streams/macbook/` and pushes to the shared git remote. The Mini pulls before each turn and shows that stream read-only. Two streams means two chats until the user merges them; that is accepted, as in Intrepidus.

## Server, WebSocket API and CLI

The reference's session object (`createSession` in ref `turn.ts`) moves into the server unchanged; the REPL and the web UI become two clients of one WebSocket API (E1).

**Server.** `Bun.serve` on `127.0.0.1:7700`, published to the tailnet by `tailscale serve`. Routes, one module each under `server/routes/`: `/ws` (the API), `/mcp` (zoom and date), `/api/*` (read-only JSON for the browser and stats; `/api/assets` takes uploads, see Media), `/artifact/*` (an artifact's sandboxed frames, see Artifacts), `/` (the built web UI). `server/app.ts` builds the parts (chat, compactor, engines, session) and hands them to the routes; `server/placement.ts` says where each device's turns run.

**Protocol: AG-UI events (E15).** The WebSocket carries AG-UI protocol events, a standard any AG-UI client can read. Both ends are ours: the server in Effect, the web UI's session store over the same events (see Web UI). Any number of clients watch the same server-owned turn. The state the events carry and the JSON of `/api/*` are schemas in `src/wire.ts`, a module with no node imports that the web UI bundles too; the server takes its types from there and encodes each `/api/*` body through its schema.

| What happens | AG-UI event | Notes |
| --- | --- | --- |
| Client connects or reconnects | `MESSAGES_SNAPSHOT` + `STATE_SNAPSHOT` | The last window of log entries and the current state; mid-run also `RUN_STARTED` and the reply streamed so far, so a client that joins mid-reply gets all of it |
| A turn starts | `RUN_STARTED` | `threadId` = stream name (`mini`), `runId` = the turn's first `user` entry |
| A `user` entry is logged (also mid-run, also from another client) | `MESSAGES_SNAPSHOT` delta or a user text message | So every client sees every message |
| Live reply text, then the `talk` entry | `TEXT_MESSAGE_START` / `CONTENT` / `END` | Message id = the entry's log index `i` |
| A `tool` entry | `TOOL_CALL_START` / `ARGS` / `END` | Tool name and JSON input |
| An `echo` entry | `TOOL_CALL_RESULT` | The capped text, as logged; `metadata: {error: true}` when the entry is flagged failed (E28), on its tool message in a `MESSAGES_SNAPSHOT` too. Not AG-UI's `ToolMessage.error`, which is a reason (the log keeps none apart from the output) and which the event lacks |
| Waiting for summaries, running, device, engine, view size, follow-ups, the models | `STATE_DELTA` | One shared state object (`SessionState`, `src/wire.ts`); each `pending` message says the `engine` it is for, whether it is `queued` (held, so it can be taken back), and carries its attachments (`media`, as stored) when it has any; `followUp` is the follow-up setting; `engines` the master's chain as the pickers show it (`{ref, label, down}`, `down` why one is unavailable), and `effort` the master's, for reading a kept pick as the chain spells it; `stopped` the engine that stopped a turn waiting for a resume (phase `needs-model`), and why; `compactions` the compactor's work per level of the tree (calls running, nodes ready and waiting for a call, calls failed and waiting for the next message; the busy levels only, told at most four times a second), and `elapsed` how long the current phase has run as of when the state was made (on the server's own clock; a client adds the time since it got it, so its own clock being off doesn't matter). Both are optional, so a client and a server from before them still decode each other |
| Usage records, failovers, errors, refusals, device offline | `CUSTOM` (`usage`, `info`) | Shown in the status line and the stats screen |
| Nothing went out on a connection for `HEARTBEAT` (5 s) | `STATE_DELTA` | The heartbeat: the state as it is now against what that connection was last told, empty when nothing changed and otherwise only what drifts by itself (`elapsed`, a subagent's), sent by the loop that sends the events, only once the connection's subscription has been empty for `HEARTBEAT`, so it never drops one or overtakes one. A frame every client decodes and applies, those from before it too: an empty or `elapsed`-only delta changes nothing they show, and a client that counts time from when it got the state counts right. The web app's link (`web/src/lib/connection.ts`) takes a socket it heard nothing on for `SILENT_MS` (10 s) for dead and closes it: a half-open connection or a laptop on a new Wi-Fi gets no close event, and before this was noticed only when the page came back to the front or the network came back. One that had delivered a frame is opened afresh at once. One that never said anything goes on the backoff. And one that had opened but not delivered its first frame (the opening `MESSAGES_SNAPSHOT` can be megabytes, more than 10 s on a slow link, and no beat can cut into a frame) doubles the window the next open socket gets, up to 16 times, so a slow link gets its snapshot in the end instead of starting the same download every 10 s; the first frame brings the window back. A handshake that hangs downloads nothing and always gets `SILENT_MS`, so a dead network is back within about 20 s of coming back. Paging the snapshots so no frame outlasts a beat is planned (docs/uniichat.md). Back from the background with an open socket kept, the link starts its silence timer again, which iOS held while the page was away. The REPL doesn't watch yet |
| Subagents (M7a) | `STATE_DELTA` (`subagents`), `SUBAGENT_STARTED` / `SUBAGENT_FINISHED` / `SUBAGENT_ERROR` | The state lists them (`{name, task, ref, effort, state, started, elapsed, label?, device?, entries?, lastLine?, why?}`, optional, so a client and a server from before them still decode each other); AG-UI's own events mark each run's start (`subagentRunId` `<name>+<n>`, the task as `description`), its end with the report as `result`, or its end without one (`code` `failed` or `stopped`). A card reads the side log from `GET /api/subagent?name&from&limit` (`SubagentLog`, at most `limit` entries from `from` on, 100 unless asked), one read at a time; a read that fails is tried again after 1 s, then 2, 4, … up to 30 s. A client sends `{"type":"tell","name","text"}`, `{"type":"stop-subagent","name"}` and `{"type":"subagent-model","name","model"}`, only while connected; what the server refuses comes back to that client as an `info` |
| Artifacts | `CUSTOM` (`artifact-draft`, `artifact`) | While a `publish_artifact` or `edit_artifact` call streams its input, `artifact-draft` carries its live draft: `{runId, id, tool, name, offset, delta, replace, closed}` (the page from `offset` on, or with `replace` the whole page; `closed` once the call's input is whole), at most every `DRAFT_EVERY`; a client that joins mid-draft gets each draft whole after `RUN_STARTED`. `artifact` (`{name, version}`) says a version was saved. A client reads the list from `GET /api/artifacts` (`ArtifactList`, src/wire.ts), the HTML from `GET /api/artifact?name&v`, and shows a version in `GET /artifact/frame?name&v` (see Artifacts). A client from before them drops the frames it can't decode |
| Thinking | `REASONING_START`, `REASONING_MESSAGE_START` / `CONTENT` / `END`, `REASONING_END`; and `CUSTOM` (`thinking`) | The text as it streams, one reasoning message `r<index>` per piece, the index being the entry it is expected before; `REASONING_END`'s `metadata` says where it was kept (`{i, ms, cut?}`) or `{dropped: true}` (nothing the turn logged came after it). A client that joins mid-thought gets it so far, as with a reply. Within the caps only (see Reasoning). `CUSTOM` `thinking` still carries the token count, for the status line, also for a thought whose text never comes. After the turn, `GET /api/reasoning?from&to` and `/api/reasoning/text?i` (see Reasoning). A client from before them drops the frames it can't decode, as it always has |
| The turn ends | `RUN_FINISHED` or `RUN_ERROR`, then `MESSAGES_SNAPSHOT` | Exactly one per `RUN_STARTED`, also on a cancel (`RUN_ERROR` "cancelled"), after the run's own entries (a cancelled tool loop's `not run: cancelled` echoes) and before anything outside it is logged; the open reply is closed first. The snapshot resyncs every client to the log, so a reply cut off before its `talk` entry disappears before its index goes to the next entry |
| Client uploads an attachment | `PUT /api/assets`, plain HTTP, the body is the file | Not an AG-UI event: bytes go over HTTP (progress, retry by hash), the message over the socket. Answers `Asset` (`src/wire.ts`): `{kind: "image", sha, mime, width, height, bytes}`, or for a video also `duration`, `frames`, `sheet`, `transcript`, `notice`; 400 empty, 413 too big or too long, 415 not a type it takes, 422 can't decode. `GET /api/assets/<sha or 12-hex prefix>[/thumb]` serves one back, with `Accept-Ranges: bytes` and one `Range` answered (206, 416 past the end), which iOS Safari needs to play a video |
| Client sends a message | a `RunAgentInput` frame | Starts a turn, or becomes a mid-run message when a turn is running; a blank text with no attachments is ignored. Its content is the text, or AG-UI's parts: a `text` part and up to four `image` / `video` parts whose `source` is `{type: "url", value: "asset:<sha256>"}`; the server looks each up in its own store and leaves out (with an `info`) one it doesn't hold. Only user messages whose ids the connection has not sent before are taken (a client may resend the whole history); an id that is the log index of a user entry with the same text names that entry and is not new, any other id is the client's own |
| A client's message is logged, or cannot be | `CUSTOM` (`ack`: `{clientId, messageId, error}`) | Before the user entry it names; `messageId` null and `error` set when the log refused it (it stays queued for the next message, and is acked again with its index when that logs it). A client tells its own messages by this, not by their text |
| Client cancels | `{"type":"abort"}` | Same as Ctrl-C in ref §10; a client sends it only while connected, so a stale one never cancels the next turn |
| Client sends a message the other way | `forwardedProps.followUp` of the `RunAgentInput`: `"steer"` or `"queue"` | Only when it differs from the session's setting (see Turn and priming, follow-ups) |
| Client sends a message for an engine | `forwardedProps.engine` of the `RunAgentInput`: a ref of the master's chain | The composer's picker or the REPL's `/model` when it was sent; none, or a ref the chain lacks (said in an `info`), is the chain's first. Picking sends nothing |
| Client takes a held message back | `{"type":"take-back","clientId"}` | Answered to every client by `CUSTOM` `taken-back`: `{clientId, text, media, error}`, the message as it was (never logged), or `text` null and `error` set when a turn already has it or the server holds no such message. Sent only while connected |
| Client changes the session's settings | `{"type":"settings","followUp"?}` | `"steer"` or `"queue"`; may wait for the connection. Saved in the data dir's `session.json`. A `lead` (a client from before the per-message model) gets that client alone an `info` to reload. Every frame, these included, is decoded by its Effect schema (`server/routes/ws.ts` `Inbound`); one that doesn't decode is dropped |
| Client resumes a stopped turn | `{"type":"resume","engine"}` | Only in `needs-model`, and sent only while connected, like an abort (the client says when it wasn't); `engine` a ref of the master's chain. One that isn't, a resume with no turn stopped, or a second resume of one stop (two clients at once), is answered with an `info` |
| A usage limit or an offline device stops a turn | `STATE_DELTA` with phase `needs-model` and `stopped`, then `RUN_ERROR`; no `info` | No failover (E4): the turn waits for a resume. Clients rely on the state coming first, to show the stop once. The resume: `RUN_STARTED` with a fresh run id, then a `CUSTOM` `info` that is the record of the stop |

The log stays the source of truth. A client's state is only a view of it, rebuilt from `MESSAGES_SNAPSHOT` on every reconnect and after every run, so there is no replay protocol.

**CLI.** `optchat` is the reference's REPL (ref §10: bracketed paste, Ctrl-C and Ctrl-Z paths, plain scrollback) talking to the server over `/ws`. `/steer` and `/queue` typed alone set the follow-up behavior; `/model` lists the master's engines (the one this REPL's messages are for, and why one is unavailable), and `/model <n>` or `/model <ref>` sets it for its next messages, sending nothing; `/resume` retries the engine that stopped a turn waiting in `needs-model`, `/resume <n|ref>` goes on with another (the REPL lists the engines when one stops; sent only while connected). It says once when a message of its own is queued for the next turn, and when one was taken back by a client. Piped, it exits once every message it sent is answered, and non-zero when one was not: the log refused it, its run ended in an error (a refusal, a cancel), a client took it back, or a turn stopped for a resume (nothing piped can resume it). `optchat view`, `stats`, `browse` and `import-*` stay local commands that read the data dir without the lock, as in the reference.

## Web UI

A phone-first single-page app in `web/`: Vite + React 19 + Tailwind 4, built into static files the server serves (E2). One page with tabs, no router framework. It is installable as a PWA, so it opens like an app from the home screen.

The chat is built from three layers, all shadcn-registry code copied into the repo:

| Layer | What | Pieces we use |
| --- | --- | --- |
| State and transport | Our own session store over the `/ws` link, reading AG-UI events (E15) | `web/src/lib/log.ts`: the log's entries by log index plus the one reply or tool call streaming in, filled from snapshots, live events and `/api/messages` pages alike; `session.ts` around it (state, markers, the queue) |
| Layout and scrolling | shadcn's official chat components (June 2026) | `MessageScroller` (anchors on user rows, prepends older history, `scrollToMessage`), `Message`, `Bubble`, `Marker` for tool lines, status and day separators |
| Rich parts | AI Elements (shadcn/ui's, October 2026), with their few AI SDK type imports swapped for our own types | `MessageResponse` (streaming markdown via Streamdown), `Tool` and `Queue` on shadcn's `Trace` and `Code Block` (the tool's input and output; messages waiting for the model, each with a take-back while held), `Plan` (a TodoWrite call's steps), `Sources` (a turn's web links) and `Reasoning` (what the model thought before a reply or tool call) on `Trace`, `Prompt Input` with shadcn's `Attachment`, `Model Selector` (with a mouse), `Context` (view size against 128 KB), and `Subagent` (presentational, for M7) |

**iOS app (E27).** `mobile/` is an Expo app whose one screen is a `react-native-webview` on the server's own `/`, at the address the user types on first launch. ## Media

Images and short videos from the phone (E19, E20). The log stays text: a message with attachments is logged as what was typed plus one marker line per attachment, the bytes live in a sidecar, and only the turn that sends them sees the pictures. hermes-optchat's sidecar was the idea; none of its code is used. Code: `src/media/` (store, normalization, video, captions, the service), `server/routes/assets.ts`, the marker grammar in `src/wire.ts`.

**Store.** `~/.optchat/assets/<sha[:2]>/<sha>.<ext>`, one store under the home for every stream, plus `<sha>.json`, the asset's metadata (`Asset` in `src/wire.ts`), written after its bytes, so an asset with metadata is whole. Shared rather than per stream because the bytes are content-addressed: two writers (M6) that store the same photo write the same file, and a git merge of two streams' assets never conflicts. The name comes only from the digest and a fixed extension table (`jpg png webp gif mp4 mov webm json`). Each file goes to a temporary name, is fsynced, renamed into place and its directory fsynced; directories are 0700, files 0600; a file already there is kept, so a write is idempotent. All of it is written while the upload is answered, long before a log line names it. persist commits it with the rest of the home and pushes it, except uploads no logged message names: a photo attached in the composer and never sent is not committed (persist writes the paths `Media.unreferenced` returns, from the log's marker lines and the frames, sheet and standard-tier copy an asset is made of, into the repo's own `.git/info/exclude` before each `git add -A`; it is never committed, and it only keeps untracked files out, so what was committed stays). Those files stay on disk, untracked, until someone removes them; a periodic cleanup of old ones is not built. Size: a standard-tier photo is ~150–400 KB, a 45 s clip its upload (up to `maxVideoBytes`, 50 MB) plus 24 frames of ~40 KB and a sheet; git keeps every committed one forever and a clone fetches all of them. **Videos are committed by persist, as uploaded** (the copy with its metadata dropped, streams as they were): GitHub warns at 50 MB and refuses a file over 100 MiB, which is why `maxVideoBytes` defaults to 50 MB. At a few photos a day that is ~1 GB a year; past that, git LFS for `assets/` or transcoding a clip to a small proxy before it is stored is the way out (neither is built). Nothing sent is ever deleted: an asset named only by a line that was compacted away is still reachable by zoom.

**Upload.** `PUT /api/assets` behind the same guard as every route (Host, Origin, `allowedLogins`). The type is read from the magic bytes, never from the client: JPEG, PNG, WebP, GIF; MP4, QuickTime, WebM. Anything else is 415 (a script named `photo.png`, SVG, PDF, HEIC). Limits: `maxImageBytes` 30 MB, `maxVideoBytes` 50 MB, `maxVideoSeconds` 180. The body is read whole (`request.arrayBuffer`), so a video is held in memory once as the upload and once as its stored copy, not three times; at most 2 uploads are worked on at once (a semaphore in `ingest`), the rest wait. Bun refuses a request body over its own `maxRequestBodySize` (128 MiB by default) before any route runs, so `serverLayer` sets it to the larger of the two limits plus 1 MiB: raising `media.maxVideoBytes` is enough. An image is decoded by sharp (libvips; prebuilt for linux-x64 and darwin-arm64, installs cleanly under Bun 1.4.2), refused past 100 megapixels, turned upright by its EXIF orientation, downscaled to the tier's long edge (standard 1568 px, the default; `?detail=high` 2576 px, the tray's "HD" toggle), and re-encoded: JPEG q85 (mozjpeg) when opaque, WebP q90 when it has transparency; the first frame of an animated GIF. sharp writes no EXIF, GPS, ICC or XMP. Only this normalized image is kept, never the original: it is what the engines get and what zoom returns. A `?detail=high` image whose long edge is past 2000 px also keeps its standard-tier copy, an image asset of its own named by `small`: a request with many pictures is sent that one (see Engines), and zoom always answers with it. The same upload gives the same bytes, so it is the same asset. The web client downscales first (canvas, JPEG q0.85 at 1568 px; a smaller image goes up as it is), so a phone photo is usually re-encoded twice at q85; the loss is small and not measured.

**Video.** ffprobe reads its length and streams; ffmpeg copies it without metadata (`-map_metadata -1`, bit-exact, streams copied: a phone writes where it was shot into the file), which is the stored video and its digest; frames are taken at one per 2 s, or 24 spread evenly over a clip longer than 48 s, at most 768 px on the long edge, each stored as an image asset (JPEG q80), plus one contact sheet (the frames in a grid with their times, within 1568 px) that thumbnails and zoom show. The audio is transcribed only by a local whisper named in `media.whisper` (a command; the 16 kHz mono WAV's path is appended, stdout is the transcript, capped at 8,000 characters); without one the asset says `audio not transcribed: no local whisper is configured`. Audio never goes to an outside service. The bytes are a stranger's, so every call is bounded: `-protocol_whitelist file` (no URL, playlist or concat input can make ffmpeg fetch anything), the demuxer forced from the sniffed type (`-f mov` for MP4 and QuickTime, `-f matroska` for WebM) instead of ffmpeg's guess, `-t <maxVideoSeconds>` on every read, a video whose ffprobe size is past 8192 px on a side or 8192×4320 in all is refused (413) before a frame is decoded, and a call that runs longer than `media.toolSeconds` (60 s) plus the clip's length is killed with SIGKILL (422), and whisper has its own limit, `media.whisperSeconds` (120 s) plus the clip's length (it loads a model before it decodes, so a minute is too tight for a big one; a whisper killed this way is only `audio not transcribed: whisper failed: it took longer than …`, the upload goes on). A whisper that hangs holds one of the 2 upload slots until it is killed, up to `whisperSeconds` plus the clip's length (5 minutes for a 180 s clip), and the other uploads wait; it is not run outside the slot because it reads the audio from the upload's temporary folder and its transcript goes into the asset's metadata, written last, so it belongs to the one ingest; a tool that exits non-zero is 422 too. ffmpeg and ffprobe must be on the server's PATH (or `media.ffmpeg`, `media.ffprobe`): this box has them, the Mini needs `brew install ffmpeg`. Images don't need them.

**Markers.** One line per attachment after the typed text (none when the text is blank), at most 4 per message (more are left out with an `info`; the web tray stops at 4):

```
[image 9d0c38e7aafe 1568x1176 212KB: a whiteboard with three arrows from Queue to Turn]
[video 4be1c09f2d73 47s, 24 frames: a cat jumps onto the desk and knocks over a cup]
```

The 12 hex digits are the digest's prefix, enough to find the asset (`GET /api/assets/<prefix>`, zoom); the caption is one line of at most 120 bytes (the model is asked for 100 characters; a longer one is cut between code points, never inside a surrogate pair, and ends in `…`) with brackets turned into parentheses. A marker is then at most 160 bytes (`[image 9d0c38e7aafe 2576x2576 30720KB: ` and a 120-byte caption), a typical one ~100. One marker with the text beside it is well inside a node (512 bytes); four typical ones fit with ~100 bytes for text; four with the longest captions (640 bytes) do not, so that message is summarized by the compactor instead of shown whole, which is why a test checks that the summary's input keeps every sha. Only trailing lines of this shape count (`splitMarkers`); one typed mid-message is text. The compactor's prompt is unchanged: it sees markers as part of the message (a test checks that the input of a marker-only message holds every sha); whether summaries keep them is for the bake-off.

**Captions.** A chain like the compactor's, `media.caption`, default `["claude-code:haiku"]`: `claude -p --safe-mode` with no tools and `prompts/caption.txt` as its system prompt, one stream-json message with the image block and the ask; api-key and openai-plan links go through their provider (the plan only with `planImages`). Usage records have role `caption`. A video is described from its sheet and the start of its transcript. Timing: the caption starts as soon as the upload is stored, in the background, usually long before the text is typed; the session never writes a marker without having waited for its caption, at most `media.captionWait` (10 s) each, then logs it with the caption or `(not described)` if none came. That is one rule in one place: `logMessage` awaits the message's captions before it writes, and each message asks for them once (`captionsOf`), so what the log keeps and what an engine is sent come from the same answer. A turn waits for the captions of exactly the messages it is about to log, together; a message that arrives meanwhile is not in that batch: it is offered to the call as soon as the run starts, ahead of anything sent later (unless it, or one sent before it, is for another device: then it waits for the next turn, see "Turn and priming"), and waits for its own captions there (a test sends photo A and photo B quickly and checks both markers carry their captions; another checks a message sent during that wait is logged before one sent during the run). A mid-run message is offered to the call after its captions are in, and logged when the call takes it with the same ones. The line is written once and never patched, so the append-only log only ever holds what was known when it was written. Rejected alternatives: a placeholder plus a later `note` entry would put a second leaf in the tree for every picture and split the description from its message in every summary; not waiting at all would log most markers undescribed. A caption call that fails is reported once and retried for the next message that names the same asset.

**Engines.** The sending turn gets the pictures after the view blocks and before the texts, so the view's cache prefix is unchanged: `claude-code` as stream-json `image` blocks with a base64 source (the shape in the Agent SDK's streaming-input docs; checked against the input schema in the installed claude 2.1.289's bundle, which takes `{type: "image", source: {type: "base64", media_type, data}}`, not by a model call), Anthropic api-key as `image` blocks, the Responses API as `input_image` with a data URL. Every picture follows a text naming it, so the model can match pictures to markers: `image <sha12>:` before an image, `video <sha12> at 0:14:` before each frame of a video, then the video's transcript or why there is none. Mid-run messages carry theirs the same way: one function (`forEngine`, in `src/session.ts`) builds the text and pictures of the opening message and of each mid-run message, from the awaited captions. After a failover the next link's opening also carries the pictures of the mid-run messages a link before took (the session keeps them for the turn), after the opening's own and against the same budget: those messages reach it in `earlier`, by their text and marker lines only, so without this it would see a picture's marker and never the picture; an engine not sent images gets the note instead.

**Picture budget** (`src/media/budget.ts`). Anthropic takes at most 100 images in a request, and with more than 20 none may be over 2000 px on a side; a turn's request grows as it goes. Each call of an engine has one budget, asked for every batch of attachments in one place (`forEngine`): the opening message's, then each mid-run message's. The attachments of one call take at most `MAX_ATTACHED` (60) of the 100; the other 40 are left to the pictures the turn's tools add, zoom's answers (at most 4 each) and Read of an image file, which nothing counts: the MCP server doesn't know which turn asked, and Claude Code's Read is its own. 40 is ten zoom answers, more than a turn uses, so a request no longer passes 100 when a turn full of video frames zooms or reads. (With 8 kept for zoom, as first built, four videos took 92 and three zooms broke the request with a 400 mid-turn.) Zoom's own pictures are always ≤ 2000 px (a high-detail image answers with its `small` copy). When a batch doesn't fit, video frames are thinned first (the same count for every video, a short clip keeping all its frames, spread evenly with the first and last in), then, when that would leave a video fewer than 4 frames, each video is shown as its contact sheet, then the first attachments in the order sent keep one picture each (an image whole, a video its sheet) and the rest are markers only, with a line saying so. A request that could pass 20 images with `ZOOM_RESERVE` (8: two zoom answers) added (or that already holds one over 2000 px, and so must stay at 20, its attachments at 12) sends every image at ≤ 2000 px: a high-detail image goes as its `small` copy. Known: a turn whose request holds a high-detail image at full size and whose tools then add more than 8 pictures passes 20 with a wide one, and the API refuses it; only `?detail=high` uploads, which have no UI yet, can cause it. Test: 4 videos and a high-detail image share 60. The same pictures go to `claude-code` and to the tool loop (Anthropic, Responses), since both get them from the session. An engine that is not sent images (openai-plan unless `media.planImages`; any engine whose `vision` is off) gets the marker lines and a note saying so, also after a failover and mid-run. Later turns see only the markers, since history is the memory; Claude Code runs a fresh process per turn (E18 hands out a process that has seen no message), so no image lingers in its context.

**zoom (E20).** `zoom(id, 1)` on a user message answers with its text and, per marker (at most 4), the image (at most 2000 px: a high-detail image answers with its standard-tier copy), or a video's contact sheet after a line with its frame count and transcript; a missing file is said in text. Same over HTTP and WS; the tool list is byte-identical. Our own tool loop's zoom (M5) stays text only: function-call outputs with images are not wired.

**Web.** The composer has an attach button (`accept="image/*,video/*"`), a separate camera button (`capture="environment"`, not Baseline, hence two), paste and drag-and-drop. Each file shows in a tray (each tile shadcn's `Attachment`, in its uploading, done or error state) with its preview (an object URL of the file itself), its upload's progress (XMLHttpRequest; fetch has none) and its error, and can be removed (a file removed, or a composer closed, while its photo is still being downscaled is never uploaded). Uploads start at once; send is on when there is text or a finished attachment and none is still uploading or failed. A logged user message shows its attachments' thumbnails from `/api/assets/<sha12>/thumb` above the bubble (a tap opens the full asset; a video plays since the server answers byte ranges) and its marker lines dimmed in the bubble. The REPL shows markers as text and can't upload.

## Reasoning

What the model thought before a reply or a tool call, kept beside the log and never in it (E29). docs/optchat.md §7 lists "logging thoughts" as a mistake: what the log holds is the memory, summarized into the tree and read by every later turn. This keeps that rule whole: nothing that builds the view, a compaction's input, a request, priming, `zoom` or the cache prefix reads the side file, the log's bytes are what they would be without it (`test/reasoning.test.ts` compares them), and parity is untouched. It exists for the web UI, which shows it as a Reasoning line above the row it came before. Code: `src/reasoning.ts` (`makePieces`, a run's pieces under the caps; `openReasoning`, the file), `src/session.ts` (its wiring), the engines, `server/agui.ts`, `server/routes/api.ts`, `web/src/lib/reasoning.ts`, `web/src/components/ai-elements/reasoning.tsx`.

**What is captured.** Each engine hands the session the thought's text as it streams (`TurnEvents.reasoning`), and its size as before (`thinking`, the status line's "thinking…"):

- `claude-code`: the text of `thinking_delta` events, or, for a thought no delta carried text for, its whole `thinking` block from the assistant message. Claude Code may send neither (ref §14 T1 saw no thinking text in the stream); then nothing is kept, and the status line still says it thinks.
- `api-key` on Anthropic: the thinking deltas' text. The signature is never kept or shown; the block goes back to the API whole, as before. On Opus 4.7 and later, the 5.x models and Haiku 5.5 the API's default `thinking.display` is `"omitted"`: thinking blocks stream with no text, so api-key keeps nothing until requests send `thinking: {display: "summarized"}`. That changes no bill but is part of the cached prefix, so it is a separate, deliberate change, not made here (see the open questions).
- The Responses API (`openai-plan`, `api-key` on OpenAI): `reasoning_summary_text` and `reasoning_text` deltas, or a finished reasoning item's `summary` when it came with no deltas. We don't ask for summaries (`reasoning.summary` is unprobed on the plan's route, and a field it refuses costs a 400), so on the plan this is usually nothing: the reasoning itself is encrypted, kept only to send back (E26).

**Pieces.** The session gathers what streams into one piece per reply or tool call it comes before: the next `talk` or `tool` entry the turn logs. A `user` (a mid-run message) or `echo` entry doesn't take it. A new thought in the same piece starts a paragraph. A piece the turn logged nothing after (a cancel, a stop for a resume, a failed call) is dropped. Live, a piece streams under the index its entry is expected at (`r<index>`) and is moved to the entry's real index when kept.

**The file.** `streams/<device>/chat/reasoning/YYYY-MM-DD.jsonl`, beside `main/` and `tree/` and split by local day as they are, one line per piece: `{i, text, engine, date, ms, cut?}`, `i` the log index of its entry, `engine` the chain entry's ref, `ms` how long it took (first token to that entry), `cut` the characters past the caps, only when some were. Append-only, one write and one fsync per line, by the lock holder; a torn last line is ended with a newline at the next start and counted as unreadable, and a line a failed write left unfinished (an ENOSPC halfway) is ended before the next piece is appended, so that piece survives a restart. The reference never looks in `chat/reasoning/`, nor does our `optchat view`.

**Caps.** `REASONING_PIECE` (30,000 characters, as `CAP`) per piece and `REASONING_TURN` (120,000) per run; the head of each is kept and the rest counted in `cut`, never streamed, so a page shows live what it shows after a reload. A piece past the turn's cap is kept with no text, as a note that it thought. The web line says "N more characters were not kept" under such a piece.

**Failures.** A write that fails is reported once per streak ("reasoning: the thinking before entry N was not kept …") and the turn goes on; a side file that can't be read at startup is reported and shows nothing. The live stream doesn't depend on the file.

**Settings.** `reasoning.keep` (default true): off, thinking is only streamed live and gone on a reload; what the file already holds is still served. `reasoning.commit` (default true): off, persist leaves `streams/*/chat/reasoning/` out of its commits (the repo's own `.git/info/exclude`, as for unsent uploads); what was committed before stays tracked, so turning it off later needs a `git rm --cached` by hand.

**Disk and git.** Thinking is often longer than the reply. At 50 turns a day with ~4 KB of thinking each that is ~200 KB a day, ~70 MB a year on disk; at most 120 KB a turn by the caps. Committed (the default), each turn's commit stores that day's file again as a new blob, so loose objects grow by the sum of the day's sizes (a day of 50 turns: ~5 MB before compression, ~1.5 MB zlib) until `git gc` packs them as deltas, which brings the history back to about the files' compressed size (~70 KB a day, ~25 MB a year); a push sends packed deltas. The log's day files already work this way, at a fraction of the size. The choice to commit: the push is the backup and, in M6, the sync, and a reasoning line that shows on the Mini but not after a restore would read as data loss. Turn `reasoning.commit` off to keep it local, or `reasoning.keep` off to keep none.

**Wire.** Live as AG-UI reasoning messages (see Protocol). After a reload the client asks `GET /api/reasoning?from&to` (at most 5,000 entries wide) for the rows it holds, after each snapshot and each older page: which entries have a piece, how long it took, its length and cut, never its text. The text is `GET /api/reasoning/text?i`, read when the reader first opens a line, so a 1,500-row history loads none of it; a 404 says the piece isn't kept, for good, and a read that fails is tried again the next time the line is opened. Both are `ReasoningHeads` and `ReasoningPiece` in `src/wire.ts` (one shape for the file's lines and the API, the head derived from it, and one rule for `cut`, `withCut`); a server from before them answers 404, which the client takes as none.

## Subagents

Phase 1 (M7a, E30): docs/optchat.md §5–§6 and the earlier gist's §9, read-only. A subagent is a background run the master starts when the user asks for one, on the server's own device, through the same engines as a turn; it outlives the turn that started it, cancelled or not. Code: `src/subagents.ts` (the supervisor), `src/mcp.ts` and `src/tools/box.ts` (the tools), `src/session.ts` (reports), `web/src/chat/subagents.tsx` (the cards).

**Tools.** The master has `spawn(name, task, model?)` and `tell(name, text)`, and `zoom("Name")`; on `claude-code` over `/mcp`, on our tool loop in its box, one tool list on every engine (it changed once, for these). `spawn` answers at once: started, or a tool error (a name that isn't a letter then up to 31 letters, digits, `-` or `_`; one taken, in any case, since a Mac's disk doesn't tell `Scout` from `scout`; an empty task; `SUBAGENTS_AT_ONCE` running, named; an unknown model, with the allowed refs; no turn running). `tell` reaches a running subagent between its tool calls (it is offered to the call as a mid-run message is, and what the call never took starts its next call); one that has ended starts again with it, within the cap. `zoom("Name")` reads its side log from entry 0, `zoom("Name", n)` from entry n, a header line (state, model, entries) then `i|kind: text` per entry, up to `SIDE_PAGE`, and says where the next page starts. Stopping one is the user's, from its card (the master never waits for one, so it has none to stop). The system prompt (`prompts/system.txt`) says "Use subagents only when the user asks for them", that each report reaches the chat as a message starting `[Name] ` which the next turn sees, and never to wait or poll for one.

**Model.** By default the spawning turn's engine and effort; the master may name `model` (`engine:model@effort`), and the user may pick one on the card, which is the subagent's from its next call (the call running keeps its own). Either way it is an engine:model of the master's chain: a ref of the chain, or one's model at another effort, clamped to what the model takes as the master's is (`runEffort`), written as the chain writes it (`canonicalRef`: the master's effort is the bare ref). Anything else is refused with the allowed refs; nothing falls back by itself. A subagent doesn't fail over or wait for a resume (E4's stop is the master's): a usage limit, an offline device or a model error fails it, and it reports why.

**A call.** The engine's `run`, with the device the server's own, the view of the turn that spawned it (or told it; else the most recent turn's; else the memory's own once every line is built), byte for byte, so on the turn's model it reads the turn's cache entry (§3.3), and one opening text: who it is (the subagent "Name", started by OptChat; the view is context only; it reads files and memory and changes nothing; its final reply is its report), its task, and on a later call its side log's newest entries within `SIDE_CONTEXT` and the messages sent to it since. One system prompt for every call, as §5 has it, not the gist's own subagent prompt: who it is goes in the message. On `claude-code` its argv is a turn's (`--tools` the master's, the same system prompt, `--replay-user-messages`) but `--permission-mode default` and `--allowedTools Read,Glob,Grep,mcp__optchat__zoom,mcp__optchat__date,mcp__optchat__read_artifact`: with `-p` and `--setting-sources ""` every other tool needs a permission nobody can give, so Edit, Write, WebFetch, WebSearch, spawn, tell, publish_artifact and edit_artifact are refused when called, as a tool result the subagent reads, and so is Bash, but for a command Claude Code's own classifier takes as read-only (`ls`, `cat`, `git log`), which recent versions run without asking (TodoWrite needs no permission and touches no file). So a subagent writes no file and changes nothing, and may run read-only commands; a `--settings` deny of `Bash(*)` would refuse those too and keep Bash listed (TODO.md). The engine's `TurnPolicy` (`SUBAGENT_POLICY`, `src/engines/registry.ts`) says all of this, `pooled: false` included; its `/mcp` key is the subagents', which refuses spawn, tell, publish_artifact and edit_artifact too; it is never warm (`pooled: false`) or primed. On our tool loop the box is the master's list (the cached prefix) whose spawn, tell, publish_artifact and edit_artifact refuse; its file tools are read-only already (M5). Thinking is not kept for a subagent.

**Side log.** `streams/<device>/agents/<Name>/log.jsonl`, beside `chat/`, in the main log's records (`{i, kind, text, size, date}`, `error` on a failed echo): its task (entry 0, `user`), the messages sent to it (`user`, `[from OptChat] …` or `[from the user] …`), its replies (`talk`), tool calls (`tool`) and results (`echo`, capped at `CAP`). Append-only, one write and one fsync per entry, by the lock holder. `agent.json` beside it says what it is: name (its folder's, or the file is left alone), task, model and effort, state, when it started and ended, why, its runs, its log's length and newest line, and `pending`, the text of a report not in the chat yet with the number of the run it ends (two runs' reports with the same words stay two); replaced whole (temp file, fsync, rename). A side log is held in memory only while its subagent runs or is listed; the others are read from the file when zoom, a later call or `/api/subagent` asks. Both are committed with the data dir when a run ends, as the main log is after a turn. Nothing that builds the view, a compaction or a request reads them: a subagent's work enters the chat's log, and so its tree, only as its report.

**Reports.** When a run ends the chat gets one `user` entry starting `[Name] ` (E23): its final reply, cut at `REPORT_MAX` with a note to zoom; or that it finished without one; or that it failed, and why, on which model; or that it was stopped, by the user or by a restart. It is made once, as the run ends and before anything else can happen to the subagent (a `tell` may start it again at once), and kept as `pending` in `agent.json` until the chat has it. The session logs it only when no turn runs: at once when idle (a loop of its own that runs no turn, leaves the phase as it was, and leaves messages parked after the log refused one where they are: they wait for a newer message), else before the next turn renders its view (one that came while the turn waited for summaries too, summarized before the view is rendered), or as the loop winds down. A report never starts a turn and is never offered to a running call, so the inbox's rules (a message's engine, device, take-back) don't apply to it; the master reads it in its next turn's view. A restart sends a pending report word for word, unless the chat holds that very `user` entry since the run ended (a crash between the chat's line and `agent.json`'s), so it is never lost and never doubled.

**Restart.** A run going on when the server stops is left `running` on disk; the next start marks it stopped ("the server restarted while it ran; nothing resumes it") and reports it. Nothing resumes it; a `tell` starts it again.

**State and wire.** `SessionState.subagents` lists every running subagent, then the newest others, up to `SUBAGENTS_SHOWN` (see Protocol). Older ones stay on disk and answer `zoom` and `tell`.

## Artifacts

M8 (E31, E32): the master can publish a page, an **artifact**: one self-contained HTML file with a name, shown beside the chat and run in a sandbox, every publish or edit a new version. The pipeline is ported from [fx0](https://github.com/vercel-labs/fx0) (Vercel Labs' design agent, Apache-2.0, commit 1337da0; NOTICE lists every file taken and third_party/fx0/LICENSE has the license), adapted from its one design per chat to many artifacts in one endless chat, and from its libfx agent, Redis and Neon to our turn engines and the data dir. Code: `src/artifacts/` (`html.ts` the validator, CSP and bootstrap; `store.ts` the folder; `tools.ts` the tools and the log's stubs; `draft.ts` the live drafts; `styles.ts` the style presets), `server/routes/artifacts.ts`, `web/src/lib/artifacts.ts`, `web/src/lib/draft-preview.ts`, `web/src/chat/artifact-card.tsx`, `web/src/chat/artifact-pane.tsx`.

**Tools.** Three, on `/mcp` beside zoom, date, spawn and tell for a `claude-code` turn (`mcp__optchat__*`), and in the tool loop's box on `openai-plan` and `api-key`; one tool list on every engine (it changed once, for these: the first request of each engine after the change rewrites the cache of the tools and system prompt, then it is stable). `publish_artifact(name, html)` makes the artifact or saves a new version of it whole; `edit_artifact(name, edits: [{old, new}])` applies exact replacements to the latest version, in order, each `old` matching exactly once in the page as the edits before it left it, and saves one new version, or saves nothing when any doesn't match (fx0's `edit_design`); `read_artifact(name, version?, from?)` reads a version (the latest by default), a `READ_PAGE` part at a time. A page the same as the latest saves no version. A publish's or an edit's echo ends with the version it saved, or found unchanged, always last and in one form (`Published landing (12.4 KB) [v3]`, `savedTag` in src/wire.ts): the one record of which call made which version, which the web reads anchored (`savedVersion`), so a name like `plan-v2` is never read as one. Every refusal comes back as the tool's error, worded so the model can fix it: a bad name, a validation error, no such artifact or version, an edit that matched 0 or 2 times. Names are a subagent's (a letter, then up to 31 letters, digits, `-` or `_`, never a path), one name in any case, written as first published; another spelling is refused. A subagent (M7a) gets `read_artifact` only: its claude may call it without asking (`--allowedTools`), publish and edit need a permission nobody gives, and the subagents' `/mcp` key and box refuse them anyway.

**Validation** (fx0's rules, `validateArtifactHtml`; the tags read by Bun's `HTMLRewriter`, lol-html, a spec tokenizer that follows foreign content, where fx0 walked them with a tokenizer of its own that a browser could disagree with: a quote in an attribute's name hid the rest of a tag, and a tag inside `<svg>`'s `<script>` or `<style>` breaks out). One document from `<!doctype html>` with exactly one html, head and body, at most `MAX_ARTIFACT_BYTES`; inline CSS and JavaScript (Canvas, animation, event handlers); images, fonts and media only as `data:` URLs; `href` only to `#fragments`, `https:` links on `<a>`, or `data:image` in SVG; no HTML comments or other markup declarations, `script src`, `<base>`, forms or `action`/`formaction`, `<iframe>`, `<object>`, `<embed>`, `meta refresh`, `javascript:`/`vbscript:` URLs (entities decoded first), `<frame>`, `<frameset>`, `<fencedframe>`, `<portal>`, `ping`, a repeated attribute (where browsers' parsers could disagree), or styles that load (`@import`, and `url()` or `image-set()` of anything but `data:` or a fragment, in `<style>` and `style=`, CSS escapes decoded first; ours). It is defense in depth: what a page does at run time is held by the sandbox, the CSPs and the bootstrap, not by this.

**Storage.** `streams/<device>/artifacts/<Name>/v<N>.html` per version and `artifact.json` (`ArtifactInfo`: its name, and per version its number, bytes, date, and `publish` or `edit`). Which call made a version is not kept here: its echo says it (above). Each file goes to a temp file, is fsynced, renamed and its folder fsynced (`replaceFile`), the version before `artifact.json`, one change at a time, by the lock holder; a crash between the two leaves a file no version names, which the next version of that number overwrites. Read at startup; a folder whose `artifact.json` doesn't read or names another folder is reported and left out. Committed with the data dir after the turn, as the logs are; `artifacts.commit: false` leaves the folder out of commits (the repo's own `.git/info/exclude`, as `reasoning.commit` does), and what was committed before stays tracked.

**The log keeps stubs (E31).** A publish carries up to 512 KB of HTML in its input and a read in its answer; logged whole, a page would be in the tree and every view until summarized, and summarizing it would take a compaction per 512 bytes of markup. So the session logs a publish's or an edit's `tool` entry with its `html` (or `edits`) replaced by its size (`mcp__optchat__publish_artifact {"name":"landing","html":"<12.4 KB of HTML, not kept in the log: read_artifact>"}`), a `read_artifact` echo as its head line only (`landing v3 of 3 (12.4 KB, 2026-10-19 14:03):` and `<12.4 KB not kept in the log: read_artifact again>`), and a publish's or edit's echo as it is (`Published landing (12.4 KB) [v3]`). One rule (`loggedText`) for the session's log and a subagent's side log, so `zoom("Name")` carries no page either; the engines say which tool an echo answers (claude-code by the result's `tool_use_id`, our tool loop by its call). The call the model made and the page it read stay in its own context for the turn; the next turn's view has the stubs, and the model reads a page again with `read_artifact`. Other entries are as before, so parity holds.

**Serving** (fx0's frame setup, every route behind `server/auth.ts`). `GET /artifact/frame?name&v` (the latest when `v` is left out) is the wrapper: our own page, no artifact markup in it, with `default-src 'none'; frame-src <host>/artifact/page; script-src 'unsafe-inline'; style-src 'unsafe-inline'; object-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'self'`, `no-referrer`, `nosniff` and a Permissions-Policy turning off camera, microphone, geolocation and the like. Its script makes an iframe with `sandbox="allow-scripts"` (no `allow-same-origin`: an opaque origin, so no cookie, storage, parent, or this origin's `/ws`, whose guard refuses `Origin: null`), `credentialless` and `no-referrer`, on `GET /artifact/page?name&v&token`, which serves the version with fx0's embedded CSP as a meta tag and its bootstrap right after the doctype (WebRTC's constructors removed, a heartbeat, a click on an `https:` link asking the parent to open it, and the frame guard, below), under the header `sandbox allow-scripts; <the same CSP>; frame-ancestors 'self'`, so it is sandboxed whoever frames it. It and `/artifact/draft` answer only a frame's load (`Sec-Fetch-Dest: iframe`, else 404): opened as a tab, a page would have no wrapper's `frame-src` to keep its own navigations in (a meta refresh, a self-navigation, an `<a ping>`, a speculation-rules prefetch all reached a listener in review).

**No frames of its own** (ours, not fx0's). Taking WebRTC's constructors from the page's window is not enough: a frame it makes has a window of its own with them, a `srcdoc` frame is not stopped by `frame-src` (nothing is fetched) and runs under the page's `allow-scripts`, and its STUN requests reach any host (review showed the datagrams arrive; Chromium ignores CSP's `webrtc 'block'`). So the bootstrap runs a frame guard (`src/artifacts/frame-guard.ts`) before any of the page's script. It takes every native it will call later (`MutationObserver` and its `observe`, `Node.prototype.removeChild`, the `parentNode`, `nodeType`, `localName`, `namespaceURI`, `addedNodes` and `NodeList` `length` getters, `item`, `createTreeWalker`, `nextNode`, `attachShadow`, `createElement`, `createElementNS`, `Reflect.apply`, `String`'s own methods) and calls them through the `Reflect.apply` it took, keeps what it finds in objects with no prototype, and walks the records by index, so a page that replaces a prototype's method or getter, an iterator, an array's setter, `Set` or `String` changes nothing it does. A subtree `MutationObserver` on the document removes every HTML `iframe`, `frame`, `fencedframe`, `object`, `embed` and `portal` (by namespace and local name, so `x:iframe` too) at the microtask checkpoint after it is inserted, before its document commits; `attachShadow` is wrapped so every shadow root is observed too; declarative shadow roots are refused (`shadowrootmode` in the markup by the validator, `setHTMLUnsafe` and `parseHTMLUnsafe` at run time); `createElement` and `createElementNS` refuse those tags outright; `document.open`, `write` and `writeln` are refused (the observer survives `document.open` in Chromium and would still see what they write, but a page has no need of them). If the guard can't be set up (a browser without one of those natives), the bootstrap puts a `script-src 'none'` policy in the head and no script of the page runs. A frame's window can't be used in the task that made it, before the observer: the frame is sandboxed as the page is, so its window is another opaque origin's and touching its `RTCPeerConnection` or its `Document.prototype.write` is a `SecurityError`. The guard and fx0's heartbeat are functions this repo type-checks and lints (`frame-guard.ts`, `bootstrap.ts`, with the few DOM names they use declared for those modules alone), inlined by `Function.prototype.toString`; `test/artifacts.test.ts` runs them from their source alone in a realm of their own, and minified, against a page that has tampered with every prototype they use. The e2e probe, with a UDP listener as its STUN server and a TCP listener, tries a `srcdoc` frame by `createElement`, by `insertAdjacentHTML`, in a closed shadow root, by `document.write`, after `document.open` has replaced the document, by the pristine `document.write` of a frame made in the same task, and inside an SVG `foreignObject` (with SVG's own `<object>` and `<embed>`, which are no frames); WebRTC from a frame's window in the same task; a dedicated and a shared worker (`worker-src 'none'` and the opaque origin stop them); and `dns-prefetch`, `preconnect`, `prefetch` and `preload` hints. No frame runs, no datagram and no TCP connection arrive, and no request leaves; with the guard taken out the same test sees the frames run and counts 63 datagrams once the probes settle (how many depends on how many frames run and how long one waits: each keeps retrying its STUN). Residuals: this is a guard in the page, measured on Chromium; WebKit's timing of the observer against a frame's commit is not measured. Resource hints a script adds are not governed by CSP: every route says `X-DNS-Prefetch-Control: off`, but whether Chromium resolves or connects for a `dns-prefetch` or `preconnect` the page adds is not measured, since the e2e's Chromium acts on no hint even on a plain page (checked against a net log), so a host name the page writes into a hint may still be looked up (TODO). The wrapper restores the frame when the heartbeat stops (a self-navigation, which its `frame-src` blocks anywhere but the page route), tells the app when the page has painted, and opens an `https:` link the page asks for in a new tab (`noopener,noreferrer`) only when the message carries the token and the click's user activation is still on. fx0 frames the page as a `data:` URL; the iOS app's WebView loads no `data:` frame (E27), so ours is a page of the server's, sandboxed twice. `GET /api/artifact?name&v` is the HTML for copy and download: `text/plain`, an attachment named `<name>-v<n>.html`, `default-src 'none'; sandbox` and `nosniff`. `GET /artifact/draft` is the empty scriptless document a draft is drawn into. `GET /api/artifacts` lists them all. A name or version that is unknown or malformed is a 404, the same either way; a name is checked as a name before it nears the disk. The service worker leaves `/artifact/*` to the server.

**Live drafts.** While a publish or an edit streams, each engine hands the session the call's input as it comes (`TurnEvents.toolInput`: claude-code's `input_json_delta`, Anthropic's `partial_json`, the Responses API's `function_call_arguments.delta`). The session decodes the `html` field as it is written (fx0's `htmlFieldExtractor`), or for an edit applies the edits written whole so far to the latest version, and sends the page so far as `CUSTOM` `artifact-draft` (`ArtifactDraft`, src/wire.ts, one shape for the server, the frame and the client), at most every `DRAFT_EVERY` (fx0's batching on a fiber) and once more as the input closes, after a flush still running; a draft past `MAX_ARTIFACT_BYTES` (which its publish would be refused for) stops there, closed. The tools' input schemas name `name` first, so a draft knows its artifact before its HTML. The client draws a draft with fx0's scriptless preview: cleaned of every script, handler, frame and remote load, patched into `/artifact/draft` (same-origin so the page can patch it, but sandboxed without `allow-scripts` and under `script-src 'none'`), and held over the pane until the saved version reports it has painted. Only the saved version runs scripts. Drafts are never kept: the run's end drops them.

**Web UI.** A publish or edit row is its tool line with a card under it: the artifact's name, its version, size and whether it was published or edited; a draft streaming in is a card of its own after the running turn's rows. A card opens the preview pane: from 1024 px a side panel beside the chat, on a phone a full-height sheet (the app's vaul Drawer, on glass). The pane (loaded on first open: 4.2 KB gzipped) has the version picker (each version, newest first, with when and its size), refresh, copy HTML, download `.html` (not in the iOS app, which loads no `blob:` download), and open in a new tab through the wrapper route. No thumbnail on the card: a preview of a page is the page, run in a frame of its own, which is not cheap enough for every card in a long chat. No separate Artifacts screen yet (a follow-up).

**Prompt and styles.** `prompts/system.txt` has an "Artifacts" section adapted from fx0's design-mode instructions, kept short since it is in every cached prefix: make one only when a visual or interactive result helps or the user asks; the format; edit over republish, all of a request's changes in one call; never paste a page's HTML into the chat; never invent facts for a page; the log keeps a call's size, so read a page again. fx0's ten DESIGN.md presets (VoltAgent's awesome-design-md, MIT, `prompts/design-md/`) are read with `read_artifact("style/<id>")`, the ids named in the tool's description: a style is 25 to 40 KB, which fx0 put in the system prompt of a chat started with it, but ours is one endless chat whose system prompt is in every request, so a style is read when the user names one ("in the style of Linear"), on any engine, by a subagent too, with no new tool.

## Tailscale, auth and operations

Nothing listens on a public interface; the tailnet is the only way in (E9).

- **Publishing:** `tailscale serve --bg --https=443 http://127.0.0.1:7700` on the Mini gives `https://<mini>.<tailnet>.ts.net` with a valid certificate. Device runners listen on their tailnet address only.
- **User auth:** `tailscale serve` adds identity headers (`Tailscale-User-Login`) to each request. The server accepts a request only if that login is in `allowedLogins` and the request came through serve on loopback; anything else gets 403.
- **Browsers:** `/ws` drives a master with `bypassPermissions`, so a web page must not reach it from someone's browser (cross-site WebSocket hijacking, DNS rebinding, or a page on the phone riding the user's own serve identity). Every route checks `Host` (`127.0.0.1:<port>`, `localhost:<port>`, `[::1]:<port>` or the host of `server.publicUrl`) and, when an `Origin` is sent, that it is the server's own origin; CLI clients send none. The threat model is written out in `server/auth.ts`.
- **Machine auth:** a device runner asks Tailscale's local WhoIs which node is calling and compares its full MagicDNS name with the server's device's, the only node it lets in (`OPTCHAT_SERVER_DEVICE`, else `defaultDevice`, as in "Multi-machine"; its URL's host plus this tailnet's suffix, so a device URL must use a name, not an IP address). Other configured devices are not let in: the server is the runner's one legitimate caller. Answers are cached per address for 10 s, and at most 4 WhoIs calls run at once. Before that it refuses any request with an `Origin` header: a page in a browser on an allowed machine is that machine's node too, and the server's runner sends none. `/mcp` is covered under zoom and date. No tokens to rotate.
- **Processes:** one launchd agent on the Mini (`optchat-server`) and one on the MacBook (`optchat-device`), each with `KeepAlive`, logs in `~/Library/Logs/optchat/`. The Mini's energy settings keep it awake.
- **Permissions:** the master runs with `bypassPermissions` (ref D9). The device's folder allowlist only sets the working directory; it does not confine `claude`, whose Bash can reach anything that user can. The boundary is who may call the runner: the server's device's node only, and no browser.
- **Persistence:** the data dir is its own git repo, committed after every turn as in ref §10, and pushed to a private remote (E10). The reasoning side files go with it unless `reasoning.commit` is off (see Reasoning). The push is the backup and, in M6, the sync. The session turns idle once the commit is made; the push runs in the background, one at a time, and a failing push is reported once until one goes through again.
- **Secrets:** the ChatGPT plan token and API keys live in the macOS Keychain (`security`, service `optchat`), never in the repo or the data dir. Off macOS (Linux, dev) they go to `~/.config/optchat/secrets.json`, mode 0600. `$OPTCHAT_SECRETS` names such a file instead, on any machine; the tests point it at an empty one.

## Usage and cost tracking

Every model call that reports usage appends one line to `usage.jsonl`, as in the reference, with more fields (E11); a failed call gets its line too when the engine says what it cost, priced on an API key and counted against its budget. A call that fails before it reports any usage (an HTTP 429 or 5xx, a network error, no access token) gets no line: it shows only as a report, and a failover it causes as the next engine's `failoverFrom`. For a turn, `failoverFrom` names the engine a usage limit or an offline device stopped before the user resumed the turn (the master doesn't fail over, E4); the stats screen lists these and the compactor's failovers together as "Engine changes". Two weeks of these lines decide the plan questions below.

```json
{"date":"2026-10-05T04:46:00Z","role":"turn|prime|compact|subagent|caption","engine":"claude-code",
 "auth":"claude-max|chatgpt-pro|api-key","model":"opus","device":"mini","level":null,
 "usage":{"input":0,"cacheRead":0,"cacheWrite":0,"output":0},
 "cold":false,"attempt":1,"failoverFrom":null,"ms":0,"effort":"high"}
```

- `effort` is the effort the call asked for (its chain entry's, else its role's as the model takes it), left out when none was sent, so one model at two efforts reads apart; the stats screen counts calls per model and effort.

- `cold` is true when the call read less than half the view from the cache. For a turn it is judged on the first request's usage (`message_start`), the one that reads the view; the token counts are the whole call's. Compactor records carry the device they ran on (the server's own machine).
- `level` is set for compactor calls, so the per-level split can be costed.
- A subagent's call (role `subagent`, M7a) also has `subagent`, its name, and `ref`, the engine it ran on as the master's chain spells it; `effort` is the effort it ran at. Every other record leaves both out.
- API-key calls also get a dollar figure from a price table in config; the server stops using the key when its monthly budget is spent and says so in the UI.
- Budget authorization uses the **local calendar month** and a strict ledger reader, separate from the tolerant `/api/usage` reader. Only a missing file (`ENOENT`) means an empty ledger. Blank lines and recognized legacy-only `{date, kind, model, usage}` envelopes are skipped; malformed JSON, unrecognized or invalid modern records, invalid dates, missing/negative/nonfinite API-key dollars and aggregate overflow block calls with a non-failover `ModelError`. Reading, validation, aggregation and balance publication are synchronous and atomic. A failed check without ambiguous charges may recover by reading the actual ledger on a later check.
- Known charges update memory before the best-effort append. If a charge arrives when its month's ledger cannot be loaded, or its dollars cannot be priced safely, that month is quarantined for the process lifetime. Later successful reads, including identical ledger lines, cannot prove that the pending charge was appended and do not reopen it. Other clean months can load normally; trusted increments and quarantine survive clock rollback. **Reconcile the ledger against all known/provider charges before restarting**; restarting alone is not reconciliation. Usage appends remain best-effort, without append acknowledgments or `fsync`: a failed write or process crash can lose a record across restart. This is not a reservation system or a strict concurrent-request spending cap.
- Provider counters must be nonnegative safe integers; OpenAI's cached input cannot exceed total input. Anthropic partial reports merge before publication. A contradictory complete TTL split is a protocol error and keeps previously valid spend; incomplete splits, or old split details made stale by a changed write aggregate, use the dearer unsplit rate. Output-only updates retain trustworthy splits. Price operands and computed dollars must be finite and nonnegative; arithmetic failure retains known tokens without inventing zero dollars, so API-key accounting quarantines the month. Malformed recognized events produce bounded errors without raw ledger/provider payloads. Failed/refused calls without an actual usage report have no spend record; explicit valid zero counts are distinct from absent/null-only reports.
- Provider captions account success or known failed spend exactly once before failover or failure publication, including composite failure causes. Only post-call accounting is masked from cancellation; the provider request remains interruptible. Refusal stays terminal (the media layer may show its placeholder), not a new failover condition. Claude Code's existing caption accounting is unchanged.

Not as shipped (`@tanstack/ai-client` 0.36.1): `webSocket()` opens its socket only inside `send()`, so a client that only watches never connects, and a close without durable offsets fails the subscription instead of reconnecting. `useChat`'s `sendMessage` also queues a message while a run streams (so a mid-run message would wait for the run to end instead of being steered into it) and shows it under a client id next to the server's logged copy. `useChat({ live: true })` over our own `SubscribeConnectionAdapter` got further (it connects at once, reconnects, rebuilds from each `MESSAGES_SNAPSHOT`), but its message model doesn't keep our ids: its stream processor attaches a `TOOL_CALL_START` to the assistant message in progress and renames pending messages, so a row's id drifted mid-turn (a tool row's open state reset, "show in chat" landed on the wrong row), and its window couldn't be merged with older pages without losing the stretch between them. What ships: our own link (`web/src/lib/connection.ts`) and session store over the same AG-UI events, keyed by log index; messages and aborts go straight to the socket, and the composer keeps its own unlogged messages in the Queue until the server's `ack` for their id.
